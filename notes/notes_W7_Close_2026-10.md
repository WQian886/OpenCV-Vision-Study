## 2. 「收」的判据：三条硬标准

一份欠账只有**同时**满足下面三条，才算「收」：

| # | 标准 | 为什么 |
|---|---|---|
| 1 | 有**测试**钉住它 | 不是注释，不是纪律，不是「我看过代码」 |
| 2 | 有**变异**证明那条测试**抓得到** | 否则「零违规」和空断言没区别 |
| 3 | 变异脚本的结论是 `unexpected results = 0` | 「没重编」和「构建失败」都不算数 |

第 2 条是本项目反复栽过的坑：

> **零违规不能证明规则在干活。**
> 一条永远绿的断言，和一条不存在的断言，在报告里长得一模一样。
> 所以每加一条规则，就要配一条**必须变红**的变异；
> 还要配一条**必须活下来**的变异 ——
> 一个只会说「红」的规则是**噪音发生器**，下一个人会把它关掉。

## 3. W7 现在是什么（全部实测）

### 3.1 算子：17 个

| 分类 | 算子 |
|---|---|
| 采集 | `image_source_dir`（文件夹）/ `image_source_video`（视频）/ `image_source_camera`（工业相机，需 MVS SDK） |
| 检测 | `color_segment` / `blob_count` / `count_check` / `pcb_inspect` / `pcb_defect_judge` |
| 定位 | `template_match` |
| 识别 | `qr_decode` |
| DL | `dl_infer`（需 ONNX Runtime） |
| 测量 | `line_fit` / `circle_fit` / `caliper_dist` / `point_point_dist` / `point_line_dist` / `angle` |

> ⚠ **「本地图像」不是一个算子。** VM 有四种图像源，W7 只实现了**三种**。
> 喂单张本地图像走的是**引擎的兜底输入 `image_path`**
> （headless 的 `--image` 就是它）——
> 流水线里可以喂单张图，但**算子库里没有「本地图像」这一项**。
> 以前 README 上写「4 种图像源」，那是把兜底路径算成算子了。
>
> ⚠ 同理，`dl_postprocess`（letterbox / NMS / YOLOv5-v8 解析）**不是一个算子** ——
> 它没注册进 `operator_factory.cpp`，是 `dl_infer` 用的辅助库。
> 算子数是 **17**，不是 18。

**旋钮的类型检查覆盖**：17 个算子的 `run()` **全部**在覆盖范围内 ——
15 个走 `param_read.h`（整数 / 小数 / 文本三个 helper），
`color_segment` 走 `hsv_params.h`（必填的 HSV 数组 / 金层标量），
`qr_decode` **一个旋钮都没有**（`defaultParams()` 返回空对象）——
它落在覆盖范围内，是因为它**没有可以被类型搞错的旋钮**。

换一种写法但语义没变，测试**必须**抓不到。
这是刻意设计的：它们证明测试判的是**语义**，不是某一种写法。

> ⚠ **第 21 轮多了 4 条另一种 SURVIVE** ——
> 它们改的是**历史快照里的数**（结项那天的表、审计的旧基线），
> 门禁**必须不报**：历史快照**本来就该**和现在不一样。
> 检查它等于要求历史等于现在，那是在**禁止历史存在**。
>
> ⇒ 38 条 SURVIVE 分**三种**，每一种验的是不同的东西：

> | 类 | 条数 | 验的是什么 |

## 5. 假 SDK 换不来的债（欠账 15 / 16）

这一节单独拎出来，因为它最容易被「片 4/片 5 收口了」这句话盖过去。

> **假 SDK 只能保证「算子的逻辑对」，
> 保证不了「算子和真 SDK 对得上」。**

假件是**照公开文档抄的**，不是抄的真头文件。
所以下面这些**只有装上真 SDK 才能验**：

**假 ONNX Runtime（欠账 15）**
- `Env::GetAllocatorInfo()` 的**返回类型在版本之间变过**（有的返回值，有的返回引用）—— 装真 SDK 时可能要加 `&`；
- `Ort::AllocatedStringPtr` 的**真实生命周期**没验过；
- `CreateTensor` 对**输入缓冲区所有权**的约定没验过。

**假 MVS SDK（欠账 16）**
- `MV_CC_DEVICE_INFO` 的 `SpecialInfo` 结构、`MV_FRAME_FRAME_INFO` 的**字段顺序**，要再对一次账；
- `MV_CC_OpenDevice` 的**默认参数**是照文档写的，真头文件里 `#ifdef __cplusplus` 那支可能不同；
- 假件的 `MV_CC_GetImageBuffer` **只吐一帧**；真 SDK 的**超时语义、帧队列、`nFrameNum` 递增**都没验过。

**但反过来不成立** —— 假件**故意比真的严**：

| 假件的做法 | 效果 |
|---|---|
| 模型不存在 → **抛异常** | 真件会接受的坏状态，假件在**同一阶段**拒绝 |
| 名字**必须对** | 真件不认的假名，假件也不认 |
| **释放即清零** | UAF 从「偶尔错」变成「**一定错**」 |
| **不提供** `MV_TRIGGER_MODE_SOFT` | 真 SDK 里根本没这个常量 → 假件在**编译期**就拒绝 |

> 所以：**假件会拒绝的，真件也会拒绝**（方向一致）；
> 假件会接受的，真件**不一定**接受（字段/枚举可能对不上）。
> 这正是欠账 15 / 16 的全部内容。

## 9. 这一轮结项本身产出的两条教训

结项不是「写个总结」。这一轮它**又抓到两个东西**。
### 9.1 「有意留下的限制」必须写清边界和重开条件

不然「有意不还」和「忘了还」分不开 —— 结项只是把一堆说不清的活儿搬进了文档。

→ `notes/atomic/at-a-limit-you-keep-needs-a-boundary.md`

### 9.2 README 上那个「能复现」的行数，其实是错的

结项要更新行数。README 上写着「121 个 C++ 文件 / **33,088 行**（口径：逐个计数，2026-10-24 实测）」，
并特别声明「旧数字这次**复现不出来** …… 于是换成一个能复现的数」。

**这一轮复现它，复现不出来** —— 而且连最接近的 ANSI 口径（33,368）也对不上。

根因：**PowerShell 5.1 的 `Get-Content` 默认按 GBK 读文件**，而源码是 UTF-8 ——
一个中文字符的第三个字节成了新的前导字节，**把行尾的 `0x0A` 当尾字节吃掉了**。

```
UTF-8:  ... 0xE4 0xB8 0xAD 0x0A ...
GBK  :  ... [一]        [前导] [尾字节 = 换行，被吞] ...
```

- 121 个文件里 **102 个**对不上，总共少算 **3,268 行**；
- **少算得最多的恰恰是中文注释最多的文件** ——
  也就是说这个指标会**奖励写得少的人**，方向完全反了；
- 真值 **36,636**，三个独立方法互相印证。

→ `notes/atomic/at-the-decoder-eats-the-newline.md`

> **口径要写到「拿别人的命令能跑出同一个数」为止。**
> 「逐个计数」不是口径，是**过程描述**。

### 9.3 结项之后又还了一笔，又抓到三个东西

结项报告写完的**当天**，还欠账 17 的第一步就抓到了三个真 bug：

1. GUI 那份判定**缺两条规则** —— 有步骤报错时它会说「最终结果: PASS」；
2. CI 的退出码是拿**末帧**推的 —— 30 帧里第 7 帧判废、末帧正常，
   **CI 判「过了」而 GUI 判「NG」**，那个是**漏检**；
3. 断言数也复现不出来 —— 记的 2048，实测 2039。

> 这三条的共同点：**全都不崩，全都是绿的。**
> 「两份一模一样的规则」就是**两份会各自漂的规则** ——
> 本项目栽过**五遍**，这是第六次。
>
> 收法是让第二份**不存在**：
> 规则收进 `frame_verdict.h`，两个调用方都用它，
> 再配一条源码守卫（判据是「**要求某个可测入口**」，
> 不是「禁止某种写法」—— 后者会被等价改写绕过）。

详见 [notes_W7_Verdict_2026-10.md](./notes_W7_Verdict_2026-10.md)。

### 9.4 结项之后还的第二笔：又抓到两件事

还欠账 18 的运行期形状，又抓到两件事：

1. **上一轮只抽了一半** —— 判定**分类**搬进了 `frame_verdict.h`，
   但「**哪一步算坏**」的判据两边还各写一遍
   （`if (info.output.contains("error")) ++frameErrors;`）。
   那是**刚建好的架构里的裂缝**：说「规则只有一份」，
   而规则其实还有半份在外面。
2. **那句判据只认一种坏法** —— 算子返回 `false`（压根没跑成）时，
   引擎把输出**置空**、失败原因写在 `info.error` 里，
   于是「输出里带 error」**数都数不到** ——
   那一步被吞掉，链继续往下跑，下游拿空输出兜底 → 数字正常 → 判 PASS。
   **信息存在，只是没人去读它。**

> 这两条的共同点：**全都不崩，全都是绿的。**
>
> 而且第 2 条的发现路径值得记：
> **用例 5 断言的是「失败被报出来了」，没断言「失败影响了判定」。**
> 第一条成立**不等于**第二条成立 —— 而第二条才是产线看的那一条。
>
> 修法：判据扩成「两种坏法都认」（`w7::isBadStep`），
> **采集也收成同一份**（`w7::FrameErrorCounter`）。
> 改口径之前先量了风险面：17 个算子里只有 3 个会 `return false`，
> **全是真失败** —— 所以**不改变任何正常流水线的行为**
> （实测：原有 129 条一条没红）。

### 9.6 结项之后还的第五笔：测试**钉住过 bug**

第五笔（解析层别丢节点）抓到的东西，比前四笔都刺眼：

5. **变异 M179 存活** —— 守卫查的是「源码里有没有这个名字」，

### 9.7 结项之后还的第六笔：「没法测」是**结论**，不是理由

第六笔（主窗口第一次进测试）抓到的最有意思的东西，是**它自己**：

> 欠账 17 一直挂着，主窗口一直不进测试目标，

> 而本项目早就写过一条规矩：
> **「没法测」和「没测」是两回事。**

> 这一笔把**同一个借口**用在主窗口上，又推翻了一次。

推翻它的做法只有三步，但每一步都是「常识」：

| 做法 | 为什么不是显然的 |
|---|---|
| 主程序源码编成**静态库** | 直觉是「测试目标再链一遍源文件」—— 那会让整个 OpenCV 那一坨**编两遍** |

而它抓到的三个真东西：

1. **上一笔的 GUI 那一半一条断言都没有** ——
   「改完不测」和「改对了」在报告里长得一模一样
2. **第十一遍「抄副本」** —— 而且是**行为一致、消息不一致**的那一种：
   GUI 说「未注册，**跳过**」，而它**并没有跳过**
   （那一步失败了，整批判 ERROR）。用户读到「跳过」会以为后面照跑了。
3. **状态和画面对不上** —— 切走时只把指针置空，表单**留在堆栈里**：

   **界面看着完全正常**，而内部已经错了。

根因是程序化调 `setSelected(true)` **不会取消上一个选中**

> **「时绿时红」的第一嫌疑不是产品不稳定，是测试自己制造了状态。**
>
> 一个抖动的测试最坏的地方是：它让人**习惯**了「这个偶尔会红」，
> 于是真出问题时也被当成「又抖了」。

### 9.8 结项之后还的第七笔：把「数字对不对得上」变成机器可查的一步

欠账 11 是**流程债**，它缺的那半步是「**强制**」：
Step 3b 把断言数**打印**出来，可文档里那十几个引用它的地方，
**没有一个会因为它过期而变红**。

这一笔加了一道新门禁 `tools/check-doc-numbers.ps1`（CI 的 Step 3c）。

**关键设计：期望值从文档里**读**出来，和实测比；不在 CI 里写死。**

```
硬编码的期望值  =  第二个副本  =  下一个会漂的东西
```

而且写死的那一份更坏：改代码的人看到 CI 红了只会去改 **CI** 里的数，
因为那是他**唯一看得见**的那个数 ——
**门禁把矛头指向了错误的方向**。

这一笔当场逮到**三处真漂移**（全是真问题，不是误报）：

1. 根 README 说 `camera` 是 **90**，实际 **93** ——
   `camera` 涨到 93 时**根 README 没跟着改**，
   而 W7 README 的套件表里写的是 93（**表对了，散文错了**）。
   这就是 `at-four-copies-of-one-number.md` 的现场版。
2. notes 体积**同一个数在根 README 里抄了两份**，其中一份从上一轮起就没更新。
3. 而且它牵出第三个问题：**量出来的数取决于怎么量** ——
   工作树直接量是 ~893 KB，**把行尾归一化成 LF 之后**（= 仓库里真正存的内容）
   是 ~891 KB，差在一个 CRLF 的文件上。
   ⇒ **字节数必须归一化之后再报**，否则换台机器 clone 一次就复现不出来。

还有一个设计上的坑：**历史快照长得和当前声明一模一样**。
结项报告里有**两张同形的表**（3.2 是结项那天的快照，3.5 是现在的数），
所以每条声明都带一个**作用域**（`After`），
只查从那个小节标题到下一个标题之间的行 ——
历史那份**既不被误报，也不被放过**。

### 9.9 结项之后还的第八笔：门禁自己**数不全**，而且**不说**

第七笔加的那道门禁（Step 3c），在 2026-10-26 早上第一次真跑的时候——

**红的。**

而且红的不是测试：26 个套件**全部通过**。
红的是 Step 3c 自己，它说「实测 18 套件 / 1804 断言」，
而文档里写的是 26 / 2371。

查下去发现：**文档是对的，实测是错的**。

那 8 个没被数到的套件，汇总行是用 `qInfo()` 打的，
而 Qt 6 在 Windows 上默认把 `qInfo` 送到**调试通道**而不是 stderr ——
ctest 看不见它们的输出。而 `set_tests_properties` 里那份
`QT_FORCE_STDERR_LOGGING=1` 的名单是**人手写的 16 个名字**，
2026-10-24 之后新加的那 8 个从没被加进去。

**这一笔最刺眼的地方在于**：Step 3c 红了，而它**指错了方向** ——
它让人去改**文档**里的 2371。照着改，真 bug 就被**写进文档**了，
门禁反而绿了。

（这和 `at-the-verdict-must-be-about-the-value-not-the-name.md` 是同一个病：
**报出来的不是那件事**。）

修法两条：

1. **名单用机器维护的那一份**（`${W7_TEST_SUITES}`）——
   抄出来的那份不会自己报警；
2. **计数的数不许比真值小而不说话** —— CI 现在会核对
   「ctest 跑了几个套件 vs 计数器看见几个」，
   少看见就红，并**点名是哪几个没看见**。

还有一个背景值得记：那道门禁**从落地起就一直是红的**，
只是**从来没被真正跑过** —— 仓库没有 remote（欠账 9）。
而这一轮的红**恰恰是环境造成的**（本机有没有那个环境变量），
真 runner 会用一台**没有你本机环境**的机器跑。

### 9.10 结项之后还的第九笔：**真跑一次，挖出三件「只有这台机器成立」**

欠账 9 的重开条件是「**仓库有 remote 的那一天**」。
2026-10-26 仓库建了（`WQian886/OpenCV-Vision-Study`），
workflow 在 `windows-2022` 上**真的启动并跑起来了**。

第一件事其实是**意外**：job 3 秒就死，

```
The job was not started because recent account payments have failed
or your spending limit needs to be increased.
```

私有仓库 + 账号消费上限。改成 **public** 之后才拿到免费分钟。

> **「job 没启动」和「job 跑失败了」在 UI 上长得不一样，但都叫红。**
> 差点把它当成「代码有问题」—— 那是**朝着错误的方向查**。

真跑起来之后，挖出**三件**东西。它们有一个共同点：
**不是代码写错了，是「这句话只在某些机器上为真」。**

| # | 什么 | 为什么本地看不见 | 修法 |
|---|---|---|---|
| 1 | W1–W4 的空 `images/` **不在 git 里** ⇒ 干净克隆上 `copy_directory` 报错 ⇒ **整个 build 挂** | 本机那个空目录**一直在** | 补四个 `.gitkeep`（`.gitignore` 里**早就写着**这条约定，只是这四个漏了） |
| 2 | W7 的 exe 靠 **PATH** 找 `Qt6Core.dll`，而 runner 的 Qt **不在 PATH 上** | 本机 PATH 里**有** Qt（装的时候写进机器 PATH 的） | `tools/ci.ps1` 从**同一个** `-QtRoot` 把 `bin` 加进 PATH |
| 3 | tesseract 的 PATH 原来写在 **YAML** 里 ⇒ 本地彩排**根本没做**这件事 | 彩排跑在同一个 shell 里，而那个 shell 恰好有 | 搬进 `tools/ci.ps1`，YAML 里那份副本**删掉** |

第 1 件还牵出一个**更深的**问题 ——
W2/W3/W4 的代码在图缺失时会**自动生成**一张：

```cpp
if (img.empty()) {
    img = generatePcbLikeImage();
    cv::imwrite(imgPath, img);   // ← 目录不存在,这一步也失败
}
```

**`imwrite` 不会替你建目录。**
所以「目录不存在」不只是 build 挂 ——
**兜底路径本身也是坏的**。

### 三条教训

1. **「本机能过」和「仓库能过」是两个问题。**
   而**只有干净克隆**才问第二个问题。
   ⇒ 「本地过了」这句话**永远只覆盖第一个**。
   要覆盖第二个，除了推上去，还可以**在本机 clone 一份再说** ——
   本笔用的就是这第二条：**便宜、快，而且能定位到具体那一步**。

2. **git 只带文件，不带目录。**
   凡是构建步骤**读**某个目录，
   那个目录要么**有文件**，要么**有 `.gitkeep`**。
   第三种状态（「本机有、仓库没有」）**在构建里就是一颗雷**。

3. **运行期按名字找 DLL，是这台机器的事实。**
   构建期用**绝对路径**，运行期用**名字搜索** ——
   ⇒ **链接成功 ≠ exe 跑得起来**。
   凡是运行期要找的东西，
   那个目录要么**在 PATH 上**（由拿到路径的那份脚本加进去），
   要么**被拷到 exe 旁边**。

> ⚠ 顺带记一个**探针自己栽的坑**，因为它比上面三条更值得记：
> 本机复现用的探针第一版调的是**裸 `cmake`**，
> 而 `cmake` **不在那个子进程的 PATH 上** ——
> 命令**压根没跑**，而 `$LASTEXITCODE` 停在 0，
> 探针于是报了一句 **"build OK"**。
>
> **一个没有真的跑东西的探针，报绿比没有探针更坏。**
> 修法两条：先把工具**找出来**（找不到 = 硬失败），
> 再**验产物在不在**（exe 没生成 = 失败，不看退出码）。

详见 [notes_CI_FirstRunnerRun_2026-10.md](./notes_CI_FirstRunnerRun_2026-10.md)。
