## 一、静默失效：不报错，只是悄悄给错答案

> 这类排在最前，因为它们**不会在开发期或测试期暴露**。本项目四种失效根子相同。

### 1.1 【实测·项目】能暴露差异的输出，必须有人消费

**现象**：`pcb_inspect` 输出 `gold_px` 字段，但全仓库**没有任何代码读它**。于是 `pcb_inspect` 与 `pcb_defect_judge` 两份金层掩膜定义早已漂开（一个绝对 `V>=80`，一个相对 `V>=0.8×板面V`），**56/56 端到端测试全绿**。

**根因**：字段存在 ≠ 字段被验证。没人读的字段等于没写。

**规避**：每加一个输出字段，问一句"谁读它"。没人读就别产出，或者当场写个消费者。

> 这是本项目"抄副本"的第四次，也是最贵的一次——**连测试都是绿的**。

### 1.2 【实测·项目】判据恒假不报错，它只是永远返回假

**现象**：`neutralness = max通道/min通道`，而 max ≥ min 恒成立，故该值恒 ≥ 1.0。把阈值调到 0.98，掩膜**全空** → `white% = 0` → 规则整条不跑 → `defects` 为空 → **报 PASS**。极性反的板被判合格。

**实测数据**（polarity.png，C1 ROI 白色像素占 ROI 面积）：

```
neutralMax = 1.15 → 4.21%    1.02 → 4.10%    1.00 → 4.05%
neutralMax = 0.98 → 0.00%    0.92 → 0.00%    0.80 → 0.00%
```

不是渐变，是 1.00 处的**断崖**。

**规避**：给每道判据配**数学边界守卫**（本项目用 `kNeutralFloor = 1.0` 钳位）。越界时**拒绝判定并报错**，不要硬撑一个 PASS。

### 1.3 【实测·项目】撞类型上限 → 判据变成"永远假"

**现象**：8 位色深上限 255。错色判据 `1.6 × 板面G`，当亮度 1.77 倍时算出 259，uint8 物理上到不了 → 条件恒假 → 报 PASS。

**实测**：临界 k = 255/(1.6×90) ≈ 1.77，与实测塌点吻合。

**规避**：阈值和量程一起算。越线时报错，不要放宽阈值硬撑。

### 1.4 【实测·项目】守卫跟着参数走了一半 → 旋钮半失灵

**现象**：`maskVMul` 参数传给了金层掩膜，蓝环那一处却走了头文件默认值。**调这个旋钮时一半生效一半不生效，且不报错**。

**根因**：默认值形参让"忘了传参"变成静默行为。

**规避**：参数一改，所有用到它的地方必须同步；不要在调用点依赖默认实参。

### 🔑 共同形状

```
条件恒假 → 中间量变 0 → 下游百分比阈值把关掉 → 结果变 PASS
```

**越靠近"成功"的那一环，越不会报错。** 这是本项目四种静默失效的共同根因。

## 三、Qt / JSON 边界坑（当日实测验证）

### 3.1 【实测】`QJsonArray::operator[]` 越界：const 安全，非 const 崩溃

**源码位置**：Qt 6.8.3 `qjsonarray.h:60-61`

```cpp
QJsonValueRef operator[](qsizetype i);        // 非 const
QJsonValue   operator[](qsizetype i) const;  // const
```

**实测输出**（当场编译运行）：

```
const OOB   type=128 isDouble=0 toInt=0      ← Undefined，安全
non-const OOB: 调用 a[5].toInt()             ← 进程崩溃
```

🔍 **异常码取决于构建类型（两次实测对比，这点容易误判）**：

| 构建 | 退出码 | 含义 |
|---|---|---|
| `CMAKE_BUILD_TYPE=Release` | `0xC0000005` | STATUS_ACCESS_VIOLATION（真的访问违例） |
| Debug（未设 build type） | `0x80000003` | STATUS_BREAKPOINT（Qt 断言先拦下） |

**Release 下的 0xC0000005 已实测确认**，与项目历史记录一致。Debug 下 Qt 的断言先触发，所以看到的是 breakpoint —— **同一个 bug，两种码**。看到 0x80000003 不要以为是"另一个问题"，它可能只是比 Release 更早地拦住了同一个错误。

### 3.2 【实测】`toInt()` 对任何非数字类型都返回 0

```
str '80'  toInt=0 isDouble=0
true      toInt=0
null      toInt=0
undefined toInt=0
```

**危害**：0 在多数阈值里是**合法值**。`["85","80","80"]` 安静地变成 `(0,0,0)`，界面上看着是自己填的值，实际跑全黑范围。

**规避**：必须用 `isDouble()` 挡，`isDouble` 返回 0 时报错。

### 3.3 【实测·项目】形状不对时报错，不补默认值

补默认值让人以为自己的配置生效了，实际跑默认阈值——属于"配置看着对、结果全错"，比直接报错难查一个数量级。

### 3.4 【实测】Qt 6.8 已移除的 API

- `QList::sorted()`：**Qt 6.8.3 头文件中已无此函数**（全头文件搜索仅命中 `QProcess` 内部无关符号），改用 `std::sort`。
- `QJsonValue::typeName()`：Qt 5 API，Qt 6 已移除，需自己映射。

## 四、变异验证：不改代码，主动制造 bug

> 本项目投入产出比最高的方法。没有它，"56/56 全绿"会一直绿下去。

### 做法

故意把实现改坏（退回绝对值、去掉守卫、写死常量），重跑测试，**看它红不红**。

### 【实测】本项目最终结果：9 个变异全部被杀

| 变异 | 含义 | 结果 |
|---|---|---|
| M11 | inspect V 退回绝对 80 | fail=3 ✅ |
| M12 | 去掉标量 `isDouble` 守卫 | fail=13 ✅ |
| M13 | 去掉 vMul 范围检查 | fail=6 ✅ |
| M14 | inspect 用写死板色 (50,90,40) | fail=1 ✅ |
| M15 | min_area_pct 退回绝对 80px | fail=5 ✅ |
| M16 | mergeDist 退回 90.0f | fail=1 ✅ |
| M17 | gold_pct 掉 `100.0*` 系数 | fail=1 ✅ |

| M19 | mergeDist 放大 3 倍 | fail=1 ✅ |

基线与还原后均为 `pass=130 fail=0`。

### 🔑 纪律一：变异活下来时，先怀疑尺子，别怀疑实现

【实测】本轮三个变异活下来，查下去**全是我检查写错了**，不是实现有 bug：

| 症状 | 我犯的错 | 正确做法 |
|---|---|---|
| `gold_pct ∈ [0,100]` 放行像素数 | **拿范围检查代替量纲检查**——像素数也落在 0~100 | 测试**独立重算**期望值再比 |
| 加了面积上限还是放行 | 按**错误假设**写检查（真实变异产出分数 0~1，不是我想的像素数） | 写断言前先确认失败的**实际形态** |
| 换板色验证"基色逐图估计"没反应 | **刺激够不到判据的门**——位移 72→64，而样本 V 在 180~255 | 先量判据**行程**，再挑落点 |
| `hi <= lo*2` 放行 | **基准跟着分子一起漂** | 钉逐档黄金值，或找变异改不到的独立基准 |

### 🔑 纪律二：基准不能来自被测对象

【实测】`refGoldPct` 原来从 `inspect.run()` 里读。变异后**两边一起缩放，恒等**——这样的基准等于没有基准。

> **验证 A 的断言，基准不能来自 A。**

已改为：测试自己调 `estimateBoardBase` + `bandMask` **独立重算**，再和算子报的数比。

### 🔑 纪律三：断言红了先怀疑尺子

【实测】本轮两次红都是我自己写错。例如断言"1.5x 与 2.0x 必须相等"，实测是 **10 vs 11**——我把探针另一组档位（0.4/0.8/1.4/1.6）的结论当成了这组（0.5/1.0/1.5/2.0）的。

### ⚠️ 成本权衡（我自己提的，不是需求）

逐档钉黄金值（`7/10/10/11`）抓得住单档偏移，但**换一张图就红**。这是拿**可维护性换检出率**。另一种做法是只钉不变量（"放大端不许爆炸"），接受检不出 M16/M18 那种单档偏移。当前选择前者。

## 五、OpenCV 判据去绝对化（当日实测验证）

### 5.1 【实测】HSV 的 H/S 严格亮度不变，只有 V 会缩放

OpenCV 4.13 实测（同一像素 ×0.5 / ×1.0 / ×1.5）：

```
BGR(50,90,40)    H=66  S=142 V=45   | H=66 S=142 V=90  | H=66 S=142 V=135
BGR(168,140,30)  H=96  S=209 V=84   | H=96 S=209 V=168 | H=96 S=209 V=252
```

**H 和 S 一格不差，V 按比例缩放。**

**推论**：去绝对化只需要动 V 那一项，不存在 H/S 撞上限的问题。

⚠️ 注意 `BGR(200,200,200) ×1.5` 时 V=255——`saturate_cast` **会削波**。削波破坏色相信息，这是另一条判据失效的路径。

### 5.2 【实测·项目】相对判据的右端也必须带 k

拿参考图的板色当常量写死，等式右边就没有 k，"相对"是假的。

本项目实测：8 张样本的板面基色 BGR = **(50,90,40)**，完全一致；25 档亮度（k=0.40~1.60）下色度漂移最大 0.0039，且 **k ≤ 0.95 时恰好为 0**——色度严格不变，漂移全部来自削波。

### 5.3 【实测·项目】逐通道中位数 vs 均值

均值会被元件和丝印拉偏。**中位数保序**（对全局乘 k 等变），且抗削波——实测哪怕 7% 像素削波（k=1.60），基色仍稳在 (50,90,40)×k。

### 5.4 【实测·项目】阈值必须是百分比，不是像素数

实测（只改分辨率不改亮度）：

```
绝对 min_area=80px：  0.5x→6  0.75x→9  1.0x→14  1.25x→18  1.5x→18  2.0x→18
占全图 0.05%（相对）： 7     10     10     11
```

同一块板被切成 6 个或 18 个"元件"。

### 5.5 【实测·项目】亮度轴 ≠ 分辨率轴，必须分开测

我第一版探针就栽在这：用 `cv::resize(img, s, k, k)` 改**分辨率**，却把表头标成"亮度"。

| 操作 | 改什么 |
|---|---|
| `cv::resize(img, s, k, k)` | 分辨率（**连带改像素统计**） |
| `img.convertTo(s, -1, k, 0)` | **只改亮度**，尺寸不变 |

混用会产生假的"缺陷"。

### 5.6 【实测·项目】形态学核尺寸必须随图缩放

固定 3×3 在 2× 图上等于噪点比原来大一倍，0.5× 上又小一倍。

### 5.7 【实测·项目】中性度判据的数学地板

穷举非黑像素，`min possible max-channel = 7`，故 `neutralness = max/min` **恒 ≥ 1.0**。

## 六、构建 / 工具链（Windows + PowerShell 5.1）

> 这部分坑最多，因为**报错信息指向完全无关的地方**。

| 坑 | 现象 | 规避 |
|---|---|---|
| `cmake` 不在 PATH | `CommandNotFoundException` | 用完整路径 `D:\Qt\Tools\CMake_64\bin\cmake.exe` |
| MSVC 找不到 `type_traits` | C1083，**像 Qt 的错其实是没 source MSVC 环境** | 构建前 `call vcvars64.bat` |
| 链接 `Qt6Cored.lib` 失败 | exit 1120，**debug 库和 release DLL 混链** | 设 `CMAKE_BUILD_TYPE Release` |
| `qInfo()` 输出消失 | 重定向到文件时 Qt 丢弃 stderr | 设 `QT_ASSUME_STDERR_HAS_CONSOLE=1` |
| commit message 乱码 | UTF-8 被当 GBK | 走文件 + `git commit -F`（**是 `commit` 的选项，不是全局选项**） |
| 全角空格 | Edit 匹配莫名失败 | 写入后扫一遍 |
| BOM-less UTF-8 `.ps1` | PowerShell 5.1 按 GBK 读 | 脚本内只用 ASCII 标识符和注释 |
| `Copy-Item` 保留 LastWriteTime | ninja 说 "no work to do" → **量的是上次的旧二进制** | 恢复文件后显式 `LastWriteTime = Get-Date` |

### 🔑 最阴险的一条

【实测·项目】最后一条会让你**测了一个根本没被修改的版本**，而结果看起来完全正常。我因此报废过整整一轮变异验证（量的是上一个变异的残留二进制）。

## 七、C++ / Qt 通用

- 【实测·项目】**`Mat&` vs `Mat*`**：OpenCV 用引用是为了**强制非空**，不是性能。别为"省一次拷贝"改成指针。
- 【实测·项目】**RAII**：`cv::Mat` / `VideoCapture` / `ifstream` 都该靠析构释放，别手动 `release()`。
- 【实测】**范围检查 ≠ 正确性检查**：值落在合法区间，不代表量纲对、单位对、语义对。
- 【实测】**临时探针用完即删**：写进 `%TEMP%`，不进仓库；跑完 `git checkout CMakeLists.txt`。

## 八、跨项目通用

1. **先量再改**——写临时基准实测，别猜。
2. **实测与推演分开写**——commit message 里绝不把推演写成测量结果。
3. **提交前扫 U+FFFD**——编码损坏会静默进 git 历史，事后极难定位。
4. **失效模式要找"共同形状"**——找形状比逐个打补丁有效（见第一节末尾）。
5. **每加一个输出字段，问"谁读它"**。

## 十、2026-10-14 续:把那个"flaky"关掉,顺手挖出一个真缺陷

> 覆盖 `86954e5` / `eac00b3`。上一轮我判过"undo_redo 偶发失败,与我的改动无关"
> —— **这个判断是错的**。教训记在第九节末尾,这里是过程。

### 10.1 偶发红的第一件事:量失败率,别急着归因

| 怎么跑 | 结果 |
|---|---|
| ctest(`build/` 目录下) | **7.0%**(200 次里 14 次) |
| 直接跑(`build/Release/` 目录下) | **0%**(200 次里 0 次) |

**同一个二进制,差别只在工作目录。** 这就把"随机"这个说法排掉了 ——
它有确定的触发条件。记下来:**看到偶发红,先量失败率并记录触发条件**
(工作目录、环境变量、机器负载),别只记一个"偶发"。

失败点每次都是同一条:`case 15「对照:A→B 回来了」`。8 次采样 8/8 一致。

### 10.2 现场长什么样

```
节点 4 个   ✓
连线 2 条   ✓
A 回来了    ✓
C→D 回来了  ✓
A→B 回来了  ✗   ← 只有这条挂
```

计数全对、身份不对 —— 第一反应是"同一条连线被记了两笔账"。
**但撤销逻辑没错**,诊断输出直接打印了撤销后的现场:

```
[DIAG] nodes=4 conns=2
[DIAG]   node {1bd4e48f...} op=blob_count
[DIAG]   node {744a46dd...} op=count_check
[DIAG]   node {d512e49b...} op=color_segment
[DIAG]   node {40995caa...} op=image_source_dir
[DIAG]   conn {1bd4e48f...} -> {744a46dd...}  sides=1/0
[DIAG]   conn {40995caa...} -> {d512e49b...}  sides=1/0
```

两条连线的 uuid 和"应该是什么"**逐字吻合**。撤销每次都精确还原了。

### 10.3 真正的写法

```cpp
while (h.undoDepth() > 0) h.undo();     // 撤销到底
...
const QUuid au = a->uuid(), ...;        // ← 在这之后才去读 a
```

而 `a` 早在 `applyPlan()` 里被 `removeNode()` **delete 掉了**。
这是货真价实的 use-after-free。

**为什么偶发**:分配器是否把 A 那块已释放内存复用给撤销时新建的节点,
取决于当次的堆布局 —— 复用到了(92%)读到的还是对的,没复用(8%)就是别的内容。

### 10.4 诊断手法:同一个二进制里 A/B 两种读法

把 bug 版读法照抄一份,和正确版并排跑,各 300 次:

| 读法 | 300 次里失败 |
|---|---|
| 删除前抓 uuid(正确) | **0**(0.00%) |
| 撤销后从裸指针取(已释放) | **24**(8.00%) |

而且 **24 次「uuid 漂移」和 24 次「查不到 A→B」完全重合** ——
是同一件事,不是两个原因。

> **一次改动让 flake 消失,只能说明"改完之后不炸"**,
> 不能说明"就是那一行导致的"。要证因果,得让两种读法在**同一个二进制**里
> 并排出数字。见 [[feedback-verification-doesnt-verify]] 第 10 条。

### 10.5 顺手挖出来的真缺陷:M7 漏了一处

M7 把"从哪个口拉出来的"存进了 `AddEdgeCmd` 和 `DeleteNodeCmd`,
**唯独漏了 `RemoveEdgeCmd`**:

```cpp
RemoveEdgeCmd::RemoveEdgeCmd(PipelineView* canvas, const QUuid& fromId, const QUuid& toId)
    : m_canvas(canvas), m_fromId(fromId), m_toId(toId) {}   // ← 没有 side

void RemoveEdgeCmd::undo() {
    ...
    m_canvas->addConnection(from, to);      // ← 方向全走默认值
}
```

用户从 A 的**下边**拉出、接到 B 的**上边**画的竖线,单独选中按 Delete、
Ctrl+Z 撤销回来:

```
fromSide: Bottom(3) -> Right(1)
toSide:   Top(2)    -> Left(0)
```

**变成横线了。** 和存盘方向丢失(用例 16-19)同一家族:
线还在、节点还在、连线关系还在,只有走向变了 —— 所以不报错、不打日志。

### 10.6 缺陷是**两处**,只测末端会漏掉中段

方向要走过 `planSelectDelete` 里的 `EdgeEndpoint` 才到得了命令:

```
EdgeEndpoint 根本没带 side   ← 第一处
RemoveEdgeCmd 根本没存 side   ← 第二处
```

先写的用例 7b 是 `new RemoveEdgeCmd(&cv, a->uuid(), b->uuid(), Bottom, Top)`,
**直接把值塞进去了**,整段传递链被跳过。所以补了 7c,走真实路径:

```
框选线 -> planSelectDelete -> EdgeEndpoint -> RemoveEdgeCmd -> exec -> undo
```

### 10.7 变异分工矩阵:证明两条用例不是抄两遍

| 变异 | 7b | 7c |
|---|---|---|
| M1 `RemoveEdgeCmd::undo` 不还原 side | **红 2** | **红 2** |
| M2 `EdgeEndpoint` 不带 side | 绿 | **红 4** |

M1 两边都杀(末端坏了,整条链都坏)。
**M2 只杀 7c** —— 中段断了,直接构造命令的 7b 完全无感。

只有矩阵长这样,才说明两条用例真的各管一段。
如果 M2 也杀 7b,就说明 7b 其实没测到它声称测的东西。
