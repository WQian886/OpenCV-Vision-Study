# 数出来的那一步也会数不全，而且它不说话

## 核心

> **量的那一步，在少算了一截的时候，报出来的数和全算对的时候长得一模一样。**
> 除非它**自己**核对 —— 而它不核对，就等于没有量过。

## 现象（2026-10-26，W7 结项之后还的第八笔）

`tools/ci.ps1` 的 Step 3c 红了：

```
FAIL: the per-suite table lists 26 suites, reality has 18
FAIL: the per-suite table adds up to 2371, reality says 1804
```

「reality says 1804」—— **实测到的数比真值少了 567**。

而 26 个套件**全部通过**。

## 根因：不是算错，是**少看见**

计数是从 ctest 的**输出文本**里正则抓的（`SUMMARY: pass= N`）。

有 8 个套件的汇总行用 `qInfo()` 打，
而 Qt 6 在 Windows 上默认把 `qInfo` 送到**调试通道**不是 stderr ——
**ctest 看不见它们的输出**。

于是计数器只抓到 18 个套件，报了 1804 条断言。

**它没有说「有 8 个我看不见」。**

## 为什么这是最贵的一种错

门禁红了 —— 看上去是好事。但它**指错了方向**：

> Step 3c 是拿实测值去对**文档**。
> 实测 1804、文档 2371 → 红 → 人去改**文档**。
> **而文档是对的。**

照着它改，真 bug 就被**写进文档**了，门禁反而绿了。

```
门禁红了 + 门禁指错方向  >  门禁没红
```

因为「门禁没红」是**没人会发现**，
而「门禁红了但指错方向」是**会把人带进沟里**。

> 这和 `at-the-verdict-must-be-about-the-value-not-the-name.md`
> 是同一个病：**报出来的不是那件事。**

## 修法：量的那一步必须能说出「本该有几个」

```powershell
$ranSuites = <从 ctest 自己的汇总里读>
if ($perSuite.Count -ne $ranSuites) {
    Fail ("ctest ran $ranSuites suites but the counter only saw $($perSuite.Count)." +
          "`n   Suites whose output never reached ctest: " + ($missed -join ', '))
}
```

关键是**点名是哪几个没看见** ——
只说「数少了」不够，因为修的人得知道去哪儿找。

配套还要防**解析器本身**跟输出脱节：
ctest 输出里的**套件行数**也必须等于 N。

## 教训

> **凡是「数出来的东西」，都要能回答「本该有几个」。**
>
> 少算几个和全算对，**在数字上长得一模一样**。

推论一：

> **少算的那部分，恰恰是最容易出事的部分。**
>
> 这一轮少算的 8 个套件，正好是**最新加的那批** ——
> 新加的东西默认「不在名单里」，而名单是人手维护的。

推论二：

> **门禁红了，先确认门禁指的方向对不对。**
>
> 「红」和「红的原因对」是两回事。
> 而要判断方向对不对，前提是**你知道真值** ——
> 所以「量的那一步要能说清它看见了几个」不是洁癖，是**必需品**。

推论三：

> **手抄的名单不会自己报警。**
>
> 这一轮那 8 个名字，是从一份**机器维护的真名单**
> （`${W7_TEST_SUITES}`）**手抄**到另一处的。
> 抄出来的那份漂了，**而且漂了没人知道** ——
> 因为计数的那一步不核对总数。
>
> ⇒ 名单要**机器维护**，不要人维护。
> ⇒ 配套 `at-extract-it-or-it-is-just-a-second-copy.md`。

推论四：

> **「没人跑过」和「跑过并且是绿的」长得不一样，
> 但都看起来像「没问题」。**
>
> 这一轮那道门禁**从落地起就一直是红的**，
> 而它在文档里被写成了「当场逮到三处真漂移」。

## 检查清单

- [ ] 这一步「数出来的东西」有「本该有几个」吗？两者在哪一步比？
- [ ] 少算的时候它是**红**，还是**报了个更小的数**？
- [ ] 它有没有**点名**是哪几个没看见？
- [ ] 名单是**机器维护**的，还是人手抄的？
- [ ] 门禁红了，我**确认过它指的方向**是对的吗？
