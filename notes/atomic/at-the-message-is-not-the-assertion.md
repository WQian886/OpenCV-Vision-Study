# 断言的红字说的是一件事，断言做的可能是另一件事

## 现象

第十轮片 2 给引擎写变异脚本，其中一条是：

> **M55**：把「兜底只补缺的」改成「兜底总是覆盖」——
> 上游给了 `image_path`，下游也该拿到兜底那个 `fallback.png`。
> 期望：**KILL**（这是引擎明写的规则，规则被破了必须红）。

实测：**SURVIVED**，96 条断言全绿。

## 为什么没红

因为那条断言**根本不在测它文案说的那件事**。

断言写的是：

```cpp
check(f.outputs.at(0).value("image_path").toString() == "from-upstream.png",
      "上游自己的 image_path 没被兜底覆盖");
```

红字说的是「**上游自己的** image_path 没被兜底覆盖」。
而它读的对象是 `f.outputs.at(0)` —— **上游自己的输出**。

问题在这儿：**兜底只动下游的 `inputs`，永远碰不到上游的输出。**
所以这条断言对它宣称要防的那个变异是**免疫**的 ——
它绿不是因为规则没被破，而是因为它压根没看那个会被破的地方。

真正会出事的地方在**下游**：

> 上游辛苦算出了 `image_path`，下游拿到的是上游那个，还是兜底那个 `fallback.png`？

而**那条断言当时一条都没有**。

也就是说：这条规则**看起来**有测试守着（红字写得很到位），
实际上**没有任何一条断言真的守着它**。

## 怎么发现的

靠**变异活了**。

一个 `Expect = KILL` 的变异活下来，只有两种解释：

1. 测试没覆盖它；
2. 判据量错了对象。

这次**两个都是**：既没覆盖下游的 inputs，那条仅有的断言又量错了对象。

> 变异活下来的时候，先怀疑断言读的**对象**对不对，
> 再怀疑覆盖够不够。顺序反了的话，会去补一堆可有可无的断言，
> 而真正缺的那条还在缺。

## 修法：断言要验**那个会被影响的对象**

改完之后：

```cpp
// 改之前:验的是上游的**输出**(兜底碰不到它,白验)
check(f.outputs.at(0).value("image_path").toString() == "from-upstream.png", ...);

// 改之后:验的是**下游拿到的 inputs**(兜底真的会动它)
check(rec->gotInputs.at(1).value("image_path").toString() == "from-upstream.png",
      "上游给了 image_path -> 下游拿到的还是**上游那个**");
```

M55 随即变红（红 1 条）。

另外还发现：上游的输出那条**可以留，但不能当成这条规则的守卫** ——
它在验「引擎没改上游的输出」，那是另一件事（另一条规则）。
两条规则，两条断言，别混成一条。

## 复发（2026-10-27）：这次不是断言，是**回读**

推这一轮的提交到 GitHub（这台机器上 `git push` 走不通，只能走 REST API），
推完照例**回读**一次，确认落地的东西和推出去的一样。

回读脚本里写着：

```powershell
$backMsg = ($readBack.commit.message | Out-String)
```

**读出来是空的。**
⇒ 结论看起来很清楚：「上一次推送把提交信息弄丢了」。

**那个结论是假的。** 那个 API（`git/commits`）返回的形状是：

```json
{ "sha": "...", "message": "……", "tree": { }, "parents": [ ] }
```

`message` 在**顶层**；`commit` 那一层是**另一个 API**
（`repos/{owner}/{repo}/commits`）才有的。
⇒ `.commit.message` 读的是**一个不存在的字段**，
它返回空不是因为信息丢了，是因为**那里根本没有信息**。

### 这次的坏处和「空断言」正好相反

| | 长什么样 | 后果 |
|---|---|---|
| 空断言（[空断言那张卡](./at-a-lint-that-finds-nothing-looks-green.md)）| 一片绿 | 以为过了 |
| 读错字段的回读 | **一个煞有介事的「发现」** | 以为坏了，去修一个没坏的东西 |

第二种更贵：它会让人去**改历史** ——
当时差点就为了一个不存在的 bug，去 force 重写一个已经发布的提交。

### 修法：回读要**和期望值比**，不要只看它是不是空

```powershell
# 改之前：只看有没有 —— 路径写错时它"有结论"（空的）
$backMsg = ($readBack.commit.message | Out-String)

# 改之后：和期望值比 —— 路径写错时它不一致 => 报错，而不是"报告发现"
$got  = ($readBack.message | Out-String).Trim()
$want = $msg.Trim()
if ($got -ne $want) { throw "read-back mismatch" }
```

> **一个「和期望值比」的检查，路径写错时会红；
> 一个「看它是不是空」的检查，路径写错时会给你一个结论。**
>
> ⇒ 回读不能只判「有没有」，要判「是不是我要的那个」。

另外：路径写错时，`jq` **安静地**返回空（不报错，也不算错），
PowerShell 5.1 在 `Set-StrictMode -Version Latest` 下才会报「属性不存在」。

> **安静的空值不是证据。**
> 一个「空」如果不能区分「东西不在」和「我看错了地方」，
> 它就不能拿来下结论 —— 只能拿来触发一次报错。

## 复发第二次（2026-10-27）：这次是**变异自己的名字**

第十一轮给普查门禁加失败路径脚本（`tools/mutate-census.ps1`）。
里面有一条变异，名字叫：

> **D：尺子坏了**（把比较那一行改成永远成立）

⇒ 这句话是**主张**。它声称的是「**那把量数的尺子**坏了」。

实际改的是 `tools/lib/DocScan.ps1` 里的**一处**比较；
而普查的数有**两处**比较（块断言一处、行断言一处）。

⇒ 名字说的是「尺子」，代码坏的是「一把尺子」。
⇒ 后果：runner 上 D 还是红的（5 条块断言的红），
**而那条红的含义和名字完全相反** ——
它说的是「**还有一把尺子活着**」，不是「尺子坏了」。

⇒ 这和上面「读错字段」是同一个形状：
**断言/变异的文案说 A，实际读/改的是 B。**
⇒ 一个 KILL/SURVIVE 的期望，如果它盯着的是**名字**，
它验证的是「名字对不对」，不是「东西坏没坏」。

### 修法：名字要**对得上**代码，而且要对得上**整把东西**

1. 变异要断的地方，按**主张的范围**来断：
   「尺子坏了」⇒ 两处比较**一起**断。
2. 每一处替换都**断言只替换了一处**（0 处 = 变异没发生 = 假的绿）。
3. 期望写成**正面的话**：「它说通过了，而且一条红都没有」。

> ⇒ **断言的红字会骗人，变异的名字也会。**
> ⇒ 两者都要用**变异自己**来验：
> 一个名字如果和它改的东西对不上，那它证明的是**别的什么东西**。

## 检查清单

- [ ] 断言的红字说的是 A，断言**读的对象**是 A 吗？
- [ ] 这条断言对**它宣称要防的那个变异**免疫吗？—— 免疫 = 白写
- [ ] 变异改动的东西，这条断言读得到吗？
- [ ] 一个 KILL 期望的变异活了：先查断言读的**对象**，再查覆盖
- [ ] 校验/回读：路径写错时，它会**报错**，还是会给你一个「发现」？
- [ ] 这个「空」能区分「东西不在」和「我看错了地方」吗？

## 推论

> **「注释会骗人，断言不会」—— 这话只对了一半。**
> 断言的**红字**也是人写的，它一样会骗人。
> 骗人的不是「断言」这个形式，是「断言声称的对象」和「断言实际读的对象」不是一回事。
>
> 所以断言不能靠红字自证，得靠**变异**：
> 断言宣称守住的规则，得有一条变异能把它打红。
> 打不红的红字，是一句愿望。

参见 `notes/atomic/at-measure-the-thing-not-the-mark.md`
（判据要量物理事实，不是量视觉替身）——
那一条讲的是「量错对象」，这一条讲的是「写错对象」，
形状一样：**断言得对准它宣称要量的那个东西**。
