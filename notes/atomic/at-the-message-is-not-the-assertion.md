# 断言的红字说的是一件事，断言做的可能是另一件事

## 现象

第十轮片 2 给引擎写变异脚本，其中一条是：

> **M55**：把「兜底只补缺的」改成「兜底总是覆盖」——
> 上游给了 `image_path`，下游也该拿到兜底那个 `fallback.png`。
> 期望：**KILL**（这是引擎明写的规则，规则被破了必须红）。

实测：**SURVIVED**，96 条断言全绿。

## 为什么没红

因为那条断言**根本不在测它文案说的那件事**。

断言写的是：

```cpp
check(f.outputs.at(0).value("image_path").toString() == "from-upstream.png",
      "上游自己的 image_path 没被兜底覆盖");
```

红字说的是「**上游自己的** image_path 没被兜底覆盖」。
而它读的对象是 `f.outputs.at(0)` —— **上游自己的输出**。

问题在这儿：**兜底只动下游的 `inputs`，永远碰不到上游的输出。**
所以这条断言对它宣称要防的那个变异是**免疫**的 ——
它绿不是因为规则没被破，而是因为它压根没看那个会被破的地方。

真正会出事的地方在**下游**：

> 上游辛苦算出了 `image_path`，下游拿到的是上游那个，还是兜底那个 `fallback.png`？

而**那条断言当时一条都没有**。

也就是说：这条规则**看起来**有测试守着（红字写得很到位），
实际上**没有任何一条断言真的守着它**。

## 怎么发现的

靠**变异活了**。

一个 `Expect = KILL` 的变异活下来，只有两种解释：

1. 测试没覆盖它；
2. 判据量错了对象。

这次**两个都是**：既没覆盖下游的 inputs，那条仅有的断言又量错了对象。

> 变异活下来的时候，先怀疑断言读的**对象**对不对，
> 再怀疑覆盖够不够。顺序反了的话，会去补一堆可有可无的断言，
> 而真正缺的那条还在缺。

## 修法：断言要验**那个会被影响的对象**

改完之后：

```cpp
// 改之前:验的是上游的**输出**(兜底碰不到它,白验)
check(f.outputs.at(0).value("image_path").toString() == "from-upstream.png", ...);

// 改之后:验的是**下游拿到的 inputs**(兜底真的会动它)
check(rec->gotInputs.at(1).value("image_path").toString() == "from-upstream.png",
      "上游给了 image_path -> 下游拿到的还是**上游那个**");
```

M55 随即变红（红 1 条）。

另外还发现：上游的输出那条**可以留，但不能当成这条规则的守卫** ——
它在验「引擎没改上游的输出」，那是另一件事（另一条规则）。
两条规则，两条断言，别混成一条。

## 检查清单

- [ ] 断言的红字说的是 A，断言**读的对象**是 A 吗？
- [ ] 这条断言对**它宣称要防的那个变异**免疫吗？—— 免疫 = 白写
- [ ] 变异改动的东西，这条断言读得到吗？
- [ ] 一个 KILL 期望的变异活了：先查断言读的**对象**，再查覆盖

## 推论

> **「注释会骗人，断言不会」—— 这话只对了一半。**
> 断言的**红字**也是人写的，它一样会骗人。
> 骗人的不是「断言」这个形式，是「断言声称的对象」和「断言实际读的对象」不是一回事。
>
> 所以断言不能靠红字自证，得靠**变异**：
> 断言宣称守住的规则，得有一条变异能把它打红。
> 打不红的红字，是一句愿望。

参见 `notes/atomic/at-measure-the-thing-not-the-mark.md`
（判据要量物理事实，不是量视觉替身）——
那一条讲的是「量错对象」，这一条讲的是「写错对象」，
形状一样：**断言得对准它宣称要量的那个东西**。
