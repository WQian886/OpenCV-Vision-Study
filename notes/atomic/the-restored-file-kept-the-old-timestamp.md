# 恢复文件没改时间戳 → 跑的是旧二进制

## 核心

2026-10-26，W2 变异验证做完要把实现**改回去**。

做法是「改之前先备份，改完用备份覆盖回来」：

```powershell
Copy-Item build\probe\color_pipeline.cpp.bak W2_ColorFilter\color_pipeline.cpp -Force
```

**文件内容确实还原了。**

但接下来：

```powershell
cmake --build ...     # -> "nothing to do"，不重编
ctest ...             # -> 8 条断言还是红的
```

**跑的是上一次那个「变异过的」二进制。**

## 为什么

`Copy-Item` 会把**源文件的时间戳**一起带过去 ——
备份是**变异之前**做的，所以它带着**变异之前**的时间戳。

还原之后，源文件的时间戳**比二进制还旧**，
MSBuild 的增量判断：**这个 .cpp 比那个 .obj 旧 → 不用编**。

```
color_pipeline.cpp   10:31   <- 备份带回来的时间戳
color_pipeline.obj   10:35   <- 变异后编出来的那次
```

⇒ **时间戳说「源文件没变过」，于是二进制留着变异版。**

## 差点怎么收场

那一瞬间我看到「8 条断言红着」，
而我已经**亲手把文件改回去了**。

两个可能的解释：

1. 「恢复失败了」—— 那就去查文件内容；
2. 「测试不稳定」—— 那就去看断言本身。

**两个都是错的。** 真相是第三种：
**文件对了，二进制没换。**

如果当时按第 2 条走，
我会给笔记里写上一句「这个测试是 flaky 的」——
**那是一句完全捏造的结论**，
而且它会**挡住后面真正该做的排查**。

## 改法

恢复之后**显式更新修改时间**：

```powershell
(Get-Item $file).LastWriteTime = Get-Date
```

**或者**，恢复之后**不直接用**，
先 `git diff` 确认内容对，
再 `touch` 一下，最后**重编**。

## 这不是新坑

memory 里有一条：「**旧二进制伪装成假红**」。
本项目**栽过一次**。

⇒ **同一个坑第二次遇到**，
说明「知道这个坑」和「不会再踩这个坑」是两件事。

⇒ 所以这次把它写成了 atomic 卡：
**写下来的坑，才不会只靠记忆挡。**

## 教训

> **「我改了文件」不等于「我改了正在跑的东西」。**
>
> 增量构建、缓存、预编译头、容器里的旧层 ——
> 它们都会让**你手上的文件**和**正在被执行的代码**分家。

⇒ 通用的做法：**改完之后，用「产出物」确认，不要用「源文件」确认。**
比如重编之后**再看一眼断言数**，
或者**故意让输出里带个版本标记**。
