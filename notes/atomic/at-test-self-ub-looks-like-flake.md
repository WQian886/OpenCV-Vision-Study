# 测试自己的 UB，会伪装成产品的偶发 bug

## 现象
`undo_redo` 套件偶发红，失败点每次都是同一条：`case 15「对照:A→B 回来了」`。
上一轮我判过"与我改动无关"，**这个判断是错的**。

## 第一件事：量失败率，而不是记一个"偶发"
| 怎么跑 | 结果 |
|---|---|
| ctest（`build/` 目录下） | **7.0%**（200 次里 14 次） |
| 直接跑（`build/Release/` 目录下） | **0%**（200 次里 0 次） |

**同一个二进制，差别只在工作目录。** 这就把"随机"排掉了——
它有确定的触发条件。

> **看到偶发红，先量失败率，并把触发条件一起记下来**
> （工作目录、环境变量、机器负载）。只记"偶发"两个字，下一轮就会重新猜。

## 真凶是测试自己
```cpp
while (h.undoDepth() > 0) h.undo();     // 撤销到底
...
const QUuid au = a->uuid(), ...;        // ← 在这之后才去读 a
```

而 `a` 早在 `applyPlan()` 里被 `removeNode()` **delete 掉了**。
测试在读已释放内存——货真价实的 use-after-free，**在被测代码之外**。

**为什么偶发**：分配器是否把 A 那块已释放内存复用给撤销时新建的节点，
取决于当次的堆布局。复用到了（92%）读到的还是对的，没复用（8%）就是别的内容。

## 手法：同一个二进制里 A/B 两种读法
把 bug 版读法照抄一份，和正确版并排跑，各 300 次：

| 读法 | 300 次里失败 |
|---|---|
| 删除前抓 uuid（正确） | **0**（0.00%） |
| 撤销后从裸指针取（已释放） | **24**（8.00%） |

而且 24 次「uuid 漂移」和 24 次「查不到 A→B」**完全重合**——
是同一件事，不是两个原因。

> **一次改动让 flake 消失，只能说明"改完之后不炸"，
> 不能说明"就是那一行导致的"。**
> 要证因果，得让两种读法在**同一个二进制**里并排出数字。

## 检查清单
- [ ] 偶发红先量失败率 + 记录触发条件，别先归因
- [ ] **测试代码也要查内存安全**——UA 也会伪装成产品 bug
- [ ] 报错稳定指向同一条断言时，那是线索不是噪声（8/8 一致）
- [ ] 想证明因果，就在同一个二进制里做 A/B 并排，别靠"改完就好了"
