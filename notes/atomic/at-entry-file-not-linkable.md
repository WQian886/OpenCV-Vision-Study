# 入口文件里的逻辑测不了：先把逻辑抽出来，再谈测试

## 一句话
> **`main()` 里的代码链接不到别的目标 —— 所以"先写测试再重构"这条路，入口文件是走不通的。**

## 现象

W6（命令行项目）写完了，功能也对，但**一条自动化测试都没有**。
而 W7 有 12 个 ctest 套件。

一开始以为是"命令行项目不方便测"，实际上是**结构问题**：

```cpp
// W6 改造前,逻辑全在这一层
int main(int argc, char** argv) {
    if      (mode == "inspect") runInspect(argc, argv, opt);
    else if (mode == "report")  runReport(argc, argv, opt);
    else                        runBaseline(opt);
}
```

`runInspect` / `runReport` / `runBaseline` 全是 `main.cpp` 里的静态函数。

## 根因

**`main.cpp` 是程序入口，别的目标链接不了它。**

想给 W6 写测试，测试目标得能调到那些函数；
而那些函数在 `main.cpp` 里，`main.cpp` 里有 `main()` ——
一个目标只能有一个 `main()`，所以 `main.cpp` 没法被链进第二个可执行文件。

于是：**逻辑在入口文件里 = 逻辑测不了。**

这不是"要不要重构"的问题，是"能不能测"的前置条件。

## 修法：拆成两层，界线画在"打不打印"上

```
w6_cli.h/.cpp    纯逻辑:查板型、找配方、跑一块板、跑一批板、拼 CSV 行
                 给输入、出结果,不打印
main.cpp         入口:解析参数、把结果打印成人话
```

界线不是按"代码量"画的，是按**"这一层有没有副作用"**画的：
`w6_cli` 不写文件、不打印、不起进程，所有输出都通过返回值/出参给回去。

抽完之后：

```cmake
add_executable(w6_cli_test tests/test_w6_cli.cpp w6_cli.cpp)
add_test(NAME w6_cli COMMAND w6_cli_test)
```

W6 从**零个** ctest 套件变成 2 个（142 + 163 条断言）。

## 仓库里已有的先例

这不是新发明。W7 早就这么干过：

```
step_scope.h     ← 从 mainwindow.cpp 抽出来的"单步执行跑哪些节点"
run_policy.h     ← 从 mainwindow.cpp 抽出来的 Run 帧循环的三条"不许 runaway"规则
frame_record.h   ← 从 mainwindow.cpp 抽出来的帧接线
```

`step_scope.h` 的头文件里写着它为什么存在 ——
因为"单步执行跑哪些节点"这条逻辑要被测，才从 `mainwindow.cpp` 里抽出来。

> 抽层不是"代码洁癖"，是**给一块逻辑开一条可测的缝**。

## 关键：抽的时候别抄副本

抽 `runReport` 的时候，"把缺陷按元件归拢"这段逻辑在 `runBaseline`
和 `runReport` 里**各写了一份** —— 正是本项目栽过四遍的坑。

改成一个共用函数：

```cpp
std::vector<ReportRow> rowsFromBoard(const std::string& relPath,
                                     const BoardResult& br,
                                     const std::string& silk,
                                     const std::string& qr);
```

**抽层这件事本身，会制造新的抄副本机会** ——
因为你要把一段逻辑"搬"到新地方，搬的过程中很容易顺手再写一份。
搬完必须回头看：**同一个概念现在有几处定义？**

## 顺带解决的两个问题

抽层之后，"入口文件"和"逻辑"分开了，于是：
- 原来藏在 `main.cpp` 里的**死代码**一眼看出来（一段什么都不做的循环）
- 参数解析和业务逻辑可以**分别**测试/推理

## 通用教训

### 1. "不好测"经常是"结构不对"的症状

不是"这个项目不适合测试"，是**逻辑被放错了地方**。

判断方法很简单：**这段逻辑现在住在哪个文件里？那个文件能被别人链接吗？**
不能 → 它永远测不了。

### 2. 抽层时最容易犯的错是"搬一份新的"

搬 = 复制 + 删除。但人更容易做成"复制 + 忘了删"或者"复制 + 改一半"。

> 抽层时对每个概念问一句：**它现在有几处定义？**

### 3. 抽层要按"有没有副作用"划界，不是按"逻辑 vs 界面"

`w6_cli` 里也有 `readSilkscreen` —— 它起 tesseract 进程、写文件，算有副作用。
但它**必须**住在这一层（它就是"跑一块板"的一部分）。
所以界线的准确说法是：

> **这一层不打印、不给全局状态赋值；输出全部通过返回值和出参。**

副作用可以有，但要有开关，好让测试能绕开慢的那部分 ——
`runReport(dir, recipeDir, doSilkscreen)` 的 `doSilkscreen` 就是这个开关。

## 检查清单

给一个项目补测试时：

- [ ] 待测逻辑住在**能被链接**的文件里？（不在 `main.cpp` / `mainwindow.cpp`）
- [ ] 抽出来的层，输出是不是全走返回值/出参？
- [ ] 抽完之后，原来那段逻辑**删干净**了吗？（不是搬一份新的）
- [ ] 抽出来的层里，有没有**重复的定义**？
- [ ] 慢的/重的部分（起进程、跑模型）留了开关给测试绕开？
