# 测试自己制造的失败：一次坏掉，永久变红

## 现象
一条测试断言"这个文件不该出现在当前目录"。

某一次跑（故意把代码改坏做变异验证）在当前目录留下了这个文件。
**把代码还原之后，这条断言仍然是红的** —— 而且红的原因和当次的改动毫无关系。

```
  [FAIL] 中间产物没有落在当前目录
```

再跑一百遍还是红的。

## 为什么比 flaky 更难查
| | 表现 |
|---|---|
| flaky | 每次随机，可能这次红下次绿 |
| **这个** | **一次坏掉，永久变红** |

flaky 至少会让人怀疑"是不是又抖了"；
这个会让人怀疑"我刚才还原干净了吗" —— 然后一遍遍去核对代码，
**根本想不到是上一次的残留**。

真正找到它的那一刻，第一反应是：
"我明明已经还原了。"

## 判据
**一条断言依赖某个东西"不存在"，那它就必须先保证那个东西真的不存在。**

也就是说：断言"没有 X"之前，先把 X 清掉。

```cpp
// ❌ 直接断言
check(!fs::exists("xxx.png"), "中间产物没有落在当前目录");

// ✅ 先清掉上一轮跑剩的
fs::remove(fs::path("xxx.png"), ec);
fs::remove(fs::path("xxx.txt"), ec);
// ... 跑 ...
check(!fs::exists("xxx.png"), "中间产物没有落在当前目录");
```

## 什么时候会踩到
- 断言"文件**不**应该出现"
- 断言"目录**不**应该有内容"
- 断言"上一次跑完应该**清空**了"
- 任何依赖**工作目录状态**的断言

## 验证办法
故意做一次会留下残留的变异，然后：

1. 还原代码
2. **不手工清理**
3. 再跑一遍

如果还是红的 —— 这就是踩到了。

## 检查清单
- [ ] 这条断言依赖的东西，会不会**被上一次跑留下来**？
- [ ] 跑之前有没有**主动清**它？
- [ ] 这个测试单独跑绿、连着跑也绿吗？（连着跑两次）
- [ ] 做完变异验证还原之后，**不手工清理**再跑一次，还是绿的吗？

> 手工清理一次就把它藏起来了 ——
> 下一个人接手时，会遇到一个"莫名其妙的红"，
> 而且**永远查不到原因**（因为跑的人早就不记得上次留下过什么）。
