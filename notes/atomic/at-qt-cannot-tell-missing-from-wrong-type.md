# 「缺失」和「类型不对」在 Qt 眼里是同一件事 —— 而它们的正确待遇完全相反

## 核心
2026-10-21，给测量类算子的坐标旋钮加类型检查时发现的。

先说结论（实测，不是照文档猜）：

```cpp
QJsonValue v = ...;
v.toInt(77);      // 77 = 传进去的默认值
```

| 值 | `toInt(77)` | `toDouble(77.5)` |
|---|---|---|
| 整数 `25` | **25** | 25 |
| 小数 `25.7` | **77** | 25.7 |
| 字符串 `"100"` | **77** | **77.5** |
| 字符串 `"abc"` | 77 | 77.5 |
| 布尔 `true` | 77 | 77.5 |
| 数组 / 对象 | 77 | 77.5 |
| `null` | 77 | 77.5 |
| key 缺失 | 77 | 77.5 |

两条反直觉的事实：

1. **字符串不会被解析** —— `"100"` 不是 100，是**默认值**。
2. **小数不会截断** —— `25.7` 不是 25，是**默认值**。

所以在 `QJsonValue` 眼里，「这个 key 不存在」和「这个 key 的类型不对」
**是同一件事**：都返回默认值。

## 为什么这件事很要紧

因为这两种情况的**正确待遇完全相反**：

| | 该怎么办 | 理由 |
|---|---|---|
| **缺失**（用户没配） | 退到**声明的默认值** | 用户没填，退回去是诚实的 —— 而且 `defaultParams()` 里写着那个值 |
| **类型不对**（用户配了，但配坏了） | **报错** | 用户填了东西，以为自己生效了，实际跑的是默认值 —— 这是「配置看着对、结果全错」 |

旧代码 `params.value("x1").toInt(默认值)` 把这两者**混成了一种**：
类型不对 → 静默按默认值算。

于是用户写进去的坐标被**整个丢掉**，算子拿默认值算，
还报出一个看着正常的距离 —— 而测量结果直接决定判废。

> 「配置看着对、结果全错」比直接报错难查一个数量级。
> 这条规矩 `operators/hsv_params.h` 里早就定下了：
> **形状不对就报错，不补默认值。**

## 教训
> **库给你的默认值，是"我分不出来"时的兜底，不是"我替你决定了"。**
> 你想区分"没配"和"配坏了"，只能自己先看类型。

推论：**`toInt()` 不带参数比写了错的值更危险** ——
Qt 的默认参数是 0，而 0 几乎从来不是那个旋钮的声明值。
所以 `toInt()` 在源码里**看不见**那个 0，lint 也看不见。

（本项目因此加了一条 lint：`setParams()` 里的 `toInt()/toDouble()`
必须带一个显式兜底，而且那个兜底不许是裸字面量。）

参见 `notes/atomic/at-a-placeholder-is-not-a-default.md`。
