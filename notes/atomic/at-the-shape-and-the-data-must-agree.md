# 声明的形状和喂进去的数据，必须是同一套约定

## 一句话
> **形状写的是 NCHW、数据喂的是 HWC —— 两边不打架，模型只是看不懂。**

## 现象

`dl_infer` 给 ONNX Runtime 喂输入张量：

```cpp
std::vector<int64_t> shape{1, 3, netInput.height, netInput.width};
auto inputTensor = Ort::Value::CreateTensor<float>(
    sc.env->GetAllocatorInfo(), f32.data, f32.total(), shape.data(), shape.size());
```

形状是 `{1, 3, H, W}` —— **NCHW**（批、通道、行、列）。
数据是 `f32.data` —— 一张 `cv::Mat`，**行优先 HWC**
（一个像素挨一个像素，每个像素 BGR 三个数）。

**两边的约定不是一回事。**

## 后果

张量"建出来了"，字节数也对得上（`H*W*3` 两边都一样），
所以**不报错、不崩溃**。

但模型收到的是：

```
R G B R G B R G B ...     ← 通道 0 这一"平面"
R G B R G B R G B ...     ← 通道 1 这一"平面"
R G B R G B R G B ...     ← 通道 2 这一"平面"
```

也就是说，模型以为自己在看三张单通道图，
实际拿到的是三张**红红红绿绿绿蓝蓝蓝**的图。

推理正常跑完，输出正常回来，只是**一个框都出不来**。

> 这类 bug 是最难查的那一类：
> 不崩、不报错、数字看着正常（日志里"推理完成 12ms"），
> **结论是错的**。

## 怎么发现的：一头一尾对照

关键不在于"我知道 NCHW 是什么"，而在于**这段代码的另一半是对的**：

输出的那半边解包成二维视图：

```cpp
cv::Mat om((int)oshape[1], (int)oshape[2], CV_32F, const_cast<float*>(odata));
```

ORT 的输出张量是 NCHW，`(oshape[1], oshape[2])` 正好是
**（通道，框）** —— **这一半是对的**。

输入和输出用**同一个模型**，一个是 NCHW、一个被当成 HWC ——
**两边一对照就露馅了**。

> 这是个通用手法：
> **同一个约定在两个地方出现时，其中一个对、另一个错，是极容易被发现的；
> 两个都错，反而没人看得出来。**

## 修法

数据也要按 NCHW 排：

```cpp
const size_t hw = static_cast<size_t>(netInput.height) * netInput.width;
std::vector<float> chw(3 * hw);
for (int y = 0; y < netInput.height; ++y) {
    const cv::Vec3f* row = f32.ptr<cv::Vec3f>(y);
    for (int x = 0; x < netInput.width; ++x) {
        const size_t i = static_cast<size_t>(y) * netInput.width + x;
        chw[0 * hw + i] = row[x][0];   // R 平面
        chw[1 * hw + i] = row[x][1];   // G 平面
        chw[2 * hw + i] = row[x][2];   // B 平面
    }
}
```

⚠ 注意通道顺序：上面已经 `cvtColor(BGR2RGB)` 过，
所以 `f32` 的通道 0 = R、1 = G、2 = B。**这里照搬，别再换一次。**

## 怎么钉住它

光"跑通了"不说明形状对。得**看送进去的东西**。

假 ONNX Runtime 把收到的张量**记下来**，于是测试可以断言：

```
张量形状是 NCHW (1,3,32,32)
通道 0 是 R 平面(混进了 0 个别的通道的值)
通道 1 是 G 平面(混进了 0 个别的通道的值)
通道 2 是 B 平面(混进了 0 个别的通道的值)
R 通道在内容区 = 0.117647
补边是 114 灰
所有值都在 0..1(归一化做了)
```

> 「通道 0 是 R 平面」这条是关键：
> 它不是"某个位置的值对不对"，而是**整个平面里没有混进别的通道的值**。
> 通道被打散时，R 平面里会混进 10/255、20/255（B 和 G 的值）——
> 一条断言就把整类错都盖住了。

## 顺带一条：维度不对要报错，不许越界

```cpp
if (oshape.size() != 3 || oshape[0] != 1) {
    out["error"] = "模型输出维度不对(期望 [1, 通道, 框数], 实际 N 维)";
    return out;
}
```

下面要按 `oshape[1]`/`oshape[2]` 取形状 ——
维度不够就是**越界访问**，崩的是整个程序，而不是"这一条流水线失败"。

> 模型不是我们以为的那个模型，是很现实的事（导出版本对不上）。
> 这种时候要**报错**，不是硬着头皮往下读。

## 教训

### 1. 声明和喂入必须**对账**

写完"我声明这是个什么形状"，问一句：
**我喂进去的字节，是按这个形状排的吗？**

对很多 API 来说，**形状只是给库看的**，
它不会替你检查数据对不对 —— 字节数对得上就收下。

### 2. 字节数对得上 ≠ 语义对得上

`H*W*3` 在 NCHW 和 HWC 里**完全一样**。
所以任何"长度检查"都抓不到这个错。

### 3. 同一约定出现两次时，一对一错最容易发现

见上面「怎么发现的」。

### 4. 假的东西要能**被检查**

假 SDK 记下收到的张量，测试才有东西可断言。
一个只会"返回固定答案"的假件，测不出数据排布对不对。

## 检查清单

- [ ] 张量/缓冲区的**形状**和**数据排布**是同一套约定吗？
- [ ] 通道顺序在预处理之后有没有被**换过两次**？
- [ ] 有没有"长度检查"被误当成了"格式检查"？
- [ ] 同一个约定在代码里出现第二次时，它和第一次**一样**吗？
- [ ] 维度/长度不对时，是**报错**还是**越界**？
