# 恢复文件后忘了碰 mtime，ninja 不重建 → 你测的是旧二进制

## 现象
做变异测试：改源码 → 构建 → 跑测试。
脚本会先"恢复原文件"，再"打上变异"。

某轮结果：**9 个变异里有 4 个活下来了**。
但那 4 个的"活下来"数值，和上一轮测的**完全一样**。

## 根因
`Copy-Item` 保留原文件的 `LastWriteTime`。

于是恢复后的文件，mtime **比新构建产物还旧** →
ninja 判定"这个 obj 已是最新" → **不重新编译**。

下一步"打上变异"如果也是 `Copy-Item` 干的，同样保留 mtime →
ninja 又说"no work to do"。

> **你测的是一个根本没被修改的版本，而结果看起来完全正常。**

## 代价
整整一轮变异验证作废 ——
4 个"存活"里至少 3 个是假的，实际代码早就是坏的。

更糟的是它**不产生任何可疑信号**：不报错、不警告，
就是给你一个看起来正常的数字。

## 修法
恢复/写入之后**显式更新时间戳**：

```powershell
function Restore-All {
    foreach ($f in $orig.Keys) {
        [IO.File]::WriteAllText($p, $orig[$f], $utf8)
        (Get-Item $p).LastWriteTime = Get-Date      # ← 关键
    }
}
```

用 `[IO.File]::WriteAllText` 而不是 `Copy-Item`，
可以顺手把编码也定死（见下一条）。

## 通用教训
### 1. 构建系统的"没活干"要当真
ninja/msbuild 说 "no work to do" 时，
先确认**输入文件的 mtime 确实比产物新**，再相信它。

### 2. 自动化脚本里，任何"写文件"都要审计时间戳
写完文件 → 显式 `LastWriteTime = Get-Date`。
这在临时脚本、测试夹具、代码生成里都一样。

### 3. 连续多轮实验尤其危险
单轮跑完看不出问题；**第二轮拿到第一轮的旧产物**就开始错。
每轮之间是唯一的安全边界。

## 附带：Windows 上的文本写入三连坑
同一次事故里还踩到（都在 PowerShell 5.1）：

| 坑 | 规避 |
|---|---|
| `Copy-Item` 保留 mtime | 显式设 `LastWriteTime` |
| `Set-Content` 默认写系统 ANSI 码页，中文变乱码 | 用 `[IO.File]::WriteAllText($p, $s, $utf8)` |
| 写完有 U+FFFD 替换字符但**不报错** | 提交前扫一遍（见下） |

### 扫替换字符（PowerShell 5.1 有效）
```powershell
$t = [IO.File]::ReadAllText($p, [Text.Encoding]::UTF8)
$n = 0
foreach ($c in $t.ToCharArray()) { if ([int]$c -eq 0xFFFD) { $n++ } }
```
编码损坏会**静默进 git 历史**，事后极难定位 —— 扫一遍成本极低。

## 复发一次(2026-10-20):同一张卡,换了个触发点

这轮做"分几个 commit"时,要把一个文件在**两个版本之间来回切**
(先切到旧版验证中间状态能编译,再切回新版)。
切回去用的是 `Copy-Item` —— **保留源文件时间戳**,
于是新版 main.cpp 的 mtime 比 .obj 还旧,ninja 判定"无需重编",只重链了链接。

结果:提交的源码是**对的**,但本地跑出来的 exe 是**旧版行为**
(报告里少扫了 9 块板:`共 8 张图` 而不是 `共 17 张图`)。

    靠人眼扫 CLI 输出才发现 —— 断言全绿,因为断言测的是 w6_cli_test,
    那个目标的 w6_cli.cpp 确实被重编了;陈旧的是 w6_pcb_defect.exe。

**所以"测试全绿"不能替代"实际跑一遍看输出"。** 这次是输出里的一个数字
(`8` vs `17`)露了馅,不是任何一条断言。

## 检查清单
批量改文件跑实验时：
- [ ] 写文件后显式更新 mtime？
- [ ] 构建输出里确认真的有 compile 行，不是只有 "no work to do"？
- [ ] 每轮之间不复用上轮的产物？

## 复发两次(2026-10-25):这次**连 build 都没触发**

前两次的触发点是「文件被写了但 mtime 没变」。
这一次连文件都没被写 —— **那个目标压根没被编译过**。

### 现场

W7 的本地构建树（`W7_VisionMasterLite/build`）里，
`w7_engine_test.exe` 是**旧的**：它来自 10-23，
而 `test_run_engine.cpp` 在那之后又加了 12 条断言。

为什么没被重编？前一轮的命令是：

```powershell
cmake --build ... --target w7_pure_test w7_run_test w7_result_render_plan_test `
                    w7_headless_test w7_vm_lite w7_test_data
```

—— **只编了那几个目标**。`w7_engine_test` 不在里面，
所以本地树里那个 exe 就一直是旧的。

### 后果：一个**看起来完全正常**的错数

那一轮把断言数写进了 README 和笔记：

```
W7 24 套件 / 2251 断言
```

真值是 **2263**。差 12 —— 正好是那个陈旧二进制少的断言数。

> 它**不产生任何可疑信号**：
> 数出来了、格式整齐、和上一轮的数只差一点点、
> 而且**总数对得上**（别处的套件都是新编的）。
> 差的那 12 条藏在**一个**套件里,谁也不会去核。

而且它**错了两轮**：
`2218`(33dd280) → 真值 2230；`2251`(eb5b8cd) → 真值 2263。

### 为什么没人发现

因为 **CI 也不数断言** —— CI 只数**套件数**
（`out of (\d+)`）。断言数一直是**人手数**的。

人手数 + 数的是**可能过期的树** = 这个数可以是错的,
而且错得**毫无痕迹**。

### 修法

**CI 自己数,而且只从自己刚建的那棵树里数。**

`tools/ci.ps1` 现在多了一步（Step 3b）：

- 再跑一次 ctest,这次带 `-V`,把每个套件的 `pass=N` 收上来;
- 断言总数**打印出来**,并写进 `build/ci/assertions.txt`;
- **不硬编码期望值** —— 硬编码的期望值就是那个会悄悄漂的数,
  正是这一步要治的病。

> 文档里引用的数字,现在**只能**来自这一行输出。

### 通用教训（补）

> **「数出来」不等于「数的是新的」。**
>
> 前两次是「文件改了但没重新编译」；
> 这一次是「**根本没要求编译那个目标**」。
> 同一个病:你量的是**一个旧的副本**,而它给出一个**看着正常的数**。
>
> 所以:
> - 要量的东西,**必须由刚跑完的那道工序产出**;
> - 报告数字的那一步,**和产出数字的那一步必须是同一次运行**。
>
> 手工量的数字,**有一天会过期**,而它过期的时候不会告诉你。

### 第四次复发（2026-10-25，第六笔）—— 以及它是怎么被抓住的

这一轮我**又**数错了：

```
我写进文档的:  W7 26 套件 / 2369 断言
CI 树实测的:   W7 26 套件 / 2371 断言
```

差 **2** 条 —— 正是我在这轮**新加**的那两条
（`paramPanelPages`：「切到占位页后，参数面板里只剩占位页」）。

**根因和前三次一模一样，而且这次更蠢**：
我**重编**了新套件、**跑**了它（52 条全绿），
但**数总数**的时候读的是**上一次**跑全套件留下的那份 ctest 输出文件 ——
那份输出是**加那两条断言之前**的。

> 我明明**刚跑过**那个套件，**刚看见**它 52 条全绿，
> 却把总数从一份**旧输出**里抄了过来。
>
> **局部的数是新的，总数是旧的** —— 而人眼对「总数」没有戒心。

**它是怎么被抓住的**：

```
== Step 3b/6  assertion count
   W7_VisionMasterLite       26 suites /   2371 assertions
   TOTAL                     29 suites /   2848 assertions
```

**上一笔刚给 CI 加的 Step 3b，当场把它逮住了。**

> 这是那一笔投入的**第一次兑现**：
> 它不检查任何东西，它只是**把数打出来** ——
> 于是「文档里的数」和「CI 树的数」**当场对不上**，
> 差 2 条在两个数字旁边**极其显眼**。
>
> 如果 Step 3b 只在**别的轮次**才跑，这 2 条就会**再躺两轮**。
>
> **「把数打出来」比「什么都不检查」强的地方就在这儿**：
> 它不判断对错，它只**让不一致变得可见**。

**这一次的处置**：

- **当场改**（`2369` → `2371`，`2846` → `2848`），**不回头改历史提交**
- 记在**这一笔**的 commit message 和笔记里 —— **记下怎么发现的**
- **不写进 Step 3b 的期望值**：硬编码一个数，它自己就会开始漂
  （那正是这一步要治的病）
