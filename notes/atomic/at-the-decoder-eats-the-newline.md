# 默认编码的解码器会吃掉换行符，于是你数出来的行数偏少

## 核心

2026-10-24，W7 结项核对数字时遇到的。

结项要更新 README 里的代码行数。README 上写着：

> 121 个 C++ 文件 / **33,088 行**（含注释与空行；口径：`git ls-files '*.cpp' '*.h'` 逐个计数，2026-10-24 实测）

而这一轮**代码一行没动**（片 5 之后就只剩笔记在改）。
那就直接数一遍：

| 口径 | 结果 |
|---|---|
| `Get-Content`（**默认编码**） | 33,368 |
| `Get-Content -Encoding UTF8` | **36,636** |
| `[IO.File]::ReadAllLines()` | **36,636** |
| 原始文件里的 `\n` 个数 | 36,616（+20：20 个文件结尾没有换行） |
| **README 记的** | **33,088** |

三个数互不相等，而且**没有一个能对上 README**。

## 根因：GBK 解码把行尾吃掉了

PowerShell 5.1 的 `Get-Content` 默认按 **ANSI 代码页（本机 936 / GBK）**读文件，
而仓库里的 `.cpp` / `.h` 是 **UTF-8**。

一个中文字符在 UTF-8 里是 **3 字节**（如 `0xE4 0xB8 0xAD`）。
GBK 解码器把它当成「双字节字符 + 一个落单字节」，
于是**第 3 个字节成了新的前导字节** —— 它后面那个字节如果是 `0x0A`（换行），
就被当成这个前导字节的**尾字节吃掉了**。

```
UTF-8:  ... 0xE4 0xB8 0xAD 0x0A ...
GBK  :  ... [一]        [前导] [尾字节=换行，被吞] ...
                          ↑ 行尾没了 → 两行合并成一行
```

**中文注释越多，少算得越多。** 实测差得最多的几个文件：

| 文件 | 真实行数 | 默认编码数 | 差 |
|---|---|---|---|
| `tests/test_operator_knobs.cpp` | 3,689 | 3,210 | **−479** |
| `tests/test_run_policy.cpp` | 1,231 | 1,034 | −197 |
| `common/pcb_core/pcb_core.cpp` | 1,179 | 1,031 | −148 |
| `common/pcb_core/pcb_core.h` | 341 | 246 | −95 |

121 个文件里 **102 个**对不上，总共少算 **3,268 行**（8.9%）。

## 为什么这个坑特别危险

它**不报错**。

- 少算的行数看起来完全正常 —— 33,368 是个「合理的行数」，不是 0，不是负数；
- 差得最多的恰恰是**注释最详细**的文件 ——
  而那些文件往往是你最引以为傲的那几个；
- **没有任何东西会提醒你**编码不一致。

这正是本项目那条老原则的一个新变体：

> **崩溃给你一个栈；静默失效给你一个看起来完全正常的结果。**

而且它有个更阴的推论：
**「代码行数」这种统计数字，会随着「注释写得多」而变小。**
而「注释写得多」恰恰是本项目提倡的 —— 于是这个指标会**奖励写得少的**，
方向完全反了。

## 修法

**凡是数行数 / 数字节数 / 按行匹配的地方，都要显式指定编码。**

```powershell
# 数 C++ 行数（含空行）
$files = git ls-files '*.cpp' '*.h'
$total = 0
$files | ForEach-Object { $total += (Get-Content -Encoding UTF8 -LiteralPath $_).Count }
```

- `-Encoding UTF8` —— 显式指定，别靠默认；
- `-LiteralPath` —— 路径里有 `[` `]` 时 `-Path` 会当通配符；
- 想连编码检测都不依赖，用 `[IO.File]::ReadAllLines($f)`（自带 BOM 探测）。

> ⚠ **PS 7 的默认值变了**（`utf8NoBOM`），同一段脚本在 5.1 和 7 上结果不同。
> 所以光写「默认」永远不安全 —— 要写**显式的那个值**。

## 推广：README 里那个「能复现」也是这么翻车的

README 上一版统计是这样写的：

> 121 个 C++ 文件 / **33,088 行**（……口径：`git ls-files '*.cpp' '*.h'` 逐个计数，2026-10-24 实测。
> 旧数字「~29310 行」这次**复现不出来** —— 当初没记口径，于是换成一个能复现的数）

**它自称能复现，实际上复现不出来** —— 而且连 ANSI 口径（33,368）都对不上。

这说明那句「口径」写得太粗：
「逐个计数」没有说**用什么读**、**怎么算行尾**，
所以下一个人拿着同样的文件、按同样的路径，**数出来的数不一样**。

> **口径要写到「拿别人的命令能跑出同一个数」为止。**
> 「逐个计数」不是口径，是**过程描述**。

这正好是 `at-unverified-number-in-comment.md` 的现场版：
> **注释里的数字没人验证过，它可能是推演出来的。**

只不过这次不是推演出来的，是**算错的** ——
而「算错」比「推演」更难发现，因为它**带着一个精确的整数**。

## 教训

> **凡是要报一个数字，先证明那个数字能被复现。**
>
> 复现的标准是：**给命令，不给过程描述。**
>
> 「用默认编码读 UTF-8 文件会少算行数」这件事，
> 最阴的地方不是它算错，而是它**错得很像对的**，
> 而且**错在注释最多的那些文件上** ——
> 指标的方向反了，奖励写得少的人。
>
> 所以：**显式指定编码**，并且**报出来的数要附一条能跑的完整命令**。

配套：`at-unverified-number-in-comment.md`（数字没人验证过）、
`at-narrow-path-encoding-ansi.md`（同一个 ANSI 陷阱在 C++ 窄串路径那边的翻版）、
`at-build-failure-looks-like-mutation-survived.md`（ANSI 解析 .ps1 的另一个后果）、
`at-reported-vs-named.md`（报出来的数 ≠ 报的是那个数）。

参见 `notes/notes_W7_Close_2026-10.md`（结项报告）。

### 现场

提交前核对「C++ 文件 / 行数」这一栏。
上一笔记的是 **131 文件 / 41,330 行**（本轮之前是 129 / 40,374）。
我按老习惯数了一遍工作树：

| 口径 | 结果 |
|---|---|
| `Get-Content`（**默认编码**） | **37,381** |
| 原始文件里的 `\n` 个数 | 41,310（+20：20 个文件结尾没有换行）→ **41,330** |
| `git show :path`（索引内容 = 将被提交的内容） | **41,330** ✓ |
| **文档里记的** | **41,330** ✓ |

**131 个文件里 114 个对不上，默认编码少算 3,931 行（9.5%）。**

### ⚠ 这次的危险方向反过来了

第一次（结项那次）数出来的**比文档多**（33,368 vs 33,088），
看着像「文档过期了」，人会去怀疑文档。

这一次数出来的**比文档少**（36,752 vs 41,330，差 4,578 行），
而**文档那个数是对的**。

> 如果我信了自己的量法，我会把一个**正确的数字改小**，
> 然后在 commit message 里写下「C++ 代码行数 37,381 行」。
>
> 那是一个**错的**、**带着精确整数**的、
> **没有任何人验证过**的数字 ——
> 和 `at-unverified-number-in-comment.md` 说的完全一样，
> 只不过这次「没人数过」的是**我刚数出来的那个数**。

### 为什么会再踩

**不是不知道这条规矩，是没想到要去查。**

我脑子里的推理链是：
「上一笔报 41,330，我数出 37,381，差 3,949 —— 肯定有一个数错了」，
于是我去**核对文档**，而不是**核对口径**。

> ⚠ **「两个数不一致」的第一反应应该是「我的量法可能不对」，
> 而不是「文档可能过期了」。**
>
> 前者是我能控制的，后者需要证据。
>
> 查卡的动作应该是「**我又要报一个数字**」的**前置步骤**，
> 不是「数字对不上」之后的**补救步骤**。

### 一个更硬的证据：这张卡里早就印着这次的数

第一次那节的表里写着：

| 文件 | 真实行数 | 默认编码数 | 差 |
|---|---|---|---|
| `tests/test_operator_knobs.cpp` | 3,689 | 3,210 | −479 |

这一轮我量同一批文件，得到的是**一模一样的 3,689 / 3,210**。
连少算的**幅度**都一字不差。

> **同一个坑、同一个量级、隔了一轮、连数都一样。**
>
> 也就是说：只要量法不变，**结果就不可能变**。
> 「量出一组新数字」这件事本身，
> 就说明**量法**是这个问题的因，而不是「文档过期」。

### 这次的处置

1. 改用**索引内容**（`git show :path`）重算 ——
   那正是**将被提交的内容**，
   也正是上一笔量 HEAD 时用的**同一个量法**
   （HEAD 算出来 = **40,374**，与上一笔文档**逐位对得上**）。

   文档里的 **131 / 41,330 是对的，没动**。

2. 拆解验证它是闭合的（不是碰巧对上）：

   ```
   HEAD 129 文件           40,374
     + 5 个改动的 C++ 文件  +224
     + 2 个新文件           +732
     ---------------------------
     = 131 文件            41,330   ✓
   ```

   **能拆开、拆完对得上**，才算这个数是「算出来的」，
   而不是「抄来的」。

3. 顺手逮住另一个**真的漂了**的数：**notes 体积**。
   根因有两条，都不是「算错了」：
   - 那个数是在**追加 atomic 卡之前**量的；
   - 同一个数在根 README 里**抄了两份**，其中一份从上一轮起就没跟着更新。

   > ⚠ **「先量数字、后改文件」= 数字立刻过期。**
   > 量的动作必须**排在所有改动之后**，
   > 否则你报出去的是一个**从来没存在过的状态**的数。

   ⚠ 而且它还牵出**第三个**问题，恰好是**这张卡的另一个变体**：

   | 口径 | 结果 |
   |---|---|
   | 工作树直接量字节 | ~893 KB |
   | **把行尾归一化成 LF 之后**（= 仓库里真正存的内容） | **~891 KB** |

   差在一个 CRLF 的文件上。

   > **同一个病的两个变体**：
   > 一个是**读**的时候把行尾吃了（少算行），
   > 一个是**存**的时候行尾不一样（字节数对不上）。
   >
   > 两个都不是「算错了」，都是**口径没写清**。
   > ⇒ **字节数必须归一化之后再报**，
   > 否则「换台机器 clone 一次」就复现不出来。

### 推广

**「数错了」和「文档过期了」是两种完全不同的错误，
而它们的处方相反。**

判据很简单：
> **你先能改的那一方，多半是你错了。**
>
> 你能让自己的量法变得和权威一致（改命令），
> 还是只能让权威变得和你一致（改文档）？

这一轮如果先动文档，就会把一个**对的**数字改坏。
而「把对的数字改坏」比「把错的数字留着」更贵 ——
后者还能被下一个人查出来，前者**看起来已经被确认过了**。
