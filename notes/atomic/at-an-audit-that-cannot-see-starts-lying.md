# 审计认不出新写法时，它会开始撒谎 —— 而且是"看起来很肯定"地撒谎

## 核心
2026-10-21，把测量类算子的旋钮读法改成
`readIntKnobs(params, kCoordKeys, ...)` 之后，旋钮审计立刻报了 **28 条**：

```
[FAIL] angle.x1 是死旋钮:defaultParams() 登记了它,当前构建的 run() 却从来没读过它
[FAIL] angle.y1 是死旋钮:...
...（28 条，正好是五个测量算子的坐标旋钮个数）
```

而这 28 个旋钮**明明被读了**。

原因很简单：审计的 `parseReads()` 只认
`params.value("x1")` 这种**字面量键名**的读法。
新读法把键名放进了一个常量：

```cpp
const QStringList kCoordKeys = {"x1", "y1", "x2", "y2"};
...
readIntKnobs(params, kCoordKeys, defaultParams(), &c, &err);
```

审计看不见 `kCoordKeys` 里是什么 → 认为这 28 个旋钮**从来没被读过**。

## 为什么误报比漏报更危险

漏报是"没查出来"，你会知道少了一块。
误报是"查出来了，而且很肯定"：

> 「angle.x1 是死旋钮 —— 界面上摆着，调了不生效」

这句话**完全可信**，但它是假的。
下一个人会去查旋钮、去查 run()、去查 defaultParams ——
**而旋钮好着呢**。他查不到原因，因为原因在审计自己身上。

> 一个查不到问题的审计比没有审计更坏，因为它让人以为有人看着。
> 这次更坏一层：**它不是查不到，它是查错了，而且说得像查对了。**

## 修法：认不出的时候，明说"我认不出"

两处一起改：

1. 审计学会新读法 —— 解析源文件里的"键名清单"常量
   （`const QStringList kCoordKeys = {...}`），
   再把 `readIntKnobs(params, kCoordKeys, ...)` 里那批键记成"被读过"。
2. 万一还是认不出（清单常量找不到、helper 的兜底不是 `defaultParams()`），
   **报"我认不出"**，而不是报"死旋钮"。

```cpp
if (!op.helperIssues.isEmpty()) {
    check(false, "%1: 审计认不出它的读法(%2)—— 这条不能判成死旋钮,得先把审计升级");
    continue;          // ← 跳过这个算子的死旋钮判定
}
```

## 教训
> **审计的识别能力跟不上代码，它就会开始撒谎。**
> 升级代码的同时必须升级审计 —— 而且要分开做、每步都能验证。

推论：每加一种新的写法，都要问一句
「**审计还认得它吗？**」
认不得的话，要么学会它，要么**明说认不出**。

> 顺带记一笔：这次 28 条假死旋钮，是靠**变异验证**之外的一次真实回归发现的 ——
> 迁移完编译通过、跑审计，红的正好是 28 条，数量和坐标旋钮个数对得上，
> 才反应过来是"审计没跟上"，不是"代码写错了"。
> **数字对得上,往往就是答案。**
