# 构建失败伪装成"变异全部存活"：你会去改一套其实有牙的测试

## 一句话
> **"测试没抓住"和"根本没编译"在结果上长得一模一样 —— 除非你让构建失败大声说话。**

## 现象

写了个变异脚本：改坏源码 → 构建 → 跑测试 → 报告红了几条 → 还原。

第一轮跑完：

```
M1  boardKindOf 退回 .string()(还原编码 bug)   RESULT=PASS   *** NOT CAUGHT
M2  runReport 退回非递归遍历(还原漏检 9 块板)   RESULT=PASS   *** NOT CAUGHT
M3  多个缺陷只写第一个                          RESULT=PASS   *** NOT CAUGHT
M4  csvEscape 不转义                           RESULT=PASS   *** NOT CAUGHT

restored: SUMMARY: pass=142 fail=0   RESULT=PASS
```

四个变异"全部存活"。第一反应当然是：**我的测试没有牙。**

## 真相

构建**根本没成功**。

脚本里直接调 `ninja`，没初始化 MSVC 环境：

```
"D:\...\cl.exe" ... -c E:\...\w6_cli.cpp
D:\opencv-src\build\install\include\opencv2/core/cvdef.h(185):
    fatal error C1083: 无法打开包括文件: "limits": No such file or directory
```

`INCLUDE` / `LIB` 缺失，`cl.exe` 连标准库头文件都找不到。
ninja 编译失败，**旧 exe 还在原地没被覆盖** —— 于是脚本跑的是旧二进制，
当然是全绿。

而脚本里那句 `& $ninja -C $build 2>&1 | Out-Null`，
把编译器的报错**一起吞掉了**。

## 为什么这个假阴性特别贵

表面结论是"我的 4 个变异全部存活"。

如果照这个结论走，接下来大概率是：
1. 去给那套测试补更多断言（补了也没用，坏的是构建）
2. 或者更糟 —— 在 commit message 里写下"**变异全部存活，本测试无牙**"

后者会**写进 git 历史**，误导后面所有读这段历史的人。

> 这比"少写一个测试"严重得多。
> 少写一个测试只是少了一点保护；
> 写错一条结论是往知识库里灌一条假信息。

## 修法

### 1. 构建失败必须抛异常

```powershell
function Build-Now {
    $out = & $ninja -C $build 2>&1
    if ($LASTEXITCODE -ne 0) {
        throw ("build failed (exit " + $LASTEXITCODE + "):`n" + ($out -join "`n"))
    }
}
```

`| Out-Null` 这类"顺手把输出藏起来"的写法，在这套脚本里就是**把错误信号销毁**。
变异脚本的构建输出是**要被检查的信号**，不是噪音。

### 2. 变异前后各跑一次基线，数字必须对得上

```
restored: pass=142 fail=0     ← 还原后
```

基线数字在每一轮之间**必须完全一致**。如果某一轮的 `pass` 数字
和基线不一样，说明**测的根本不是同一份代码**。

### 3. 看见"全员存活"先怀疑自己

规则：**N 个变异全部存活，比 1 个变异存活更可疑。**

真的全都存活，概率极低 —— 除非测试根本没在测。
所以"全存活"的第一反应应该是"我的实验装置坏了"，
而不是"我的测试没牙"。

## 通用教训

### 1. 实验装置要能自证

一个能得出结论的实验装置，必须能**报告"我这次没跑成"**。
不能只报告"我这次的结果是 X"。

> 「构建失败」和「测试没抓到」在结果上是同一个值（PASS），
> 说明这个装置**分辨率不够**。

### 2. 静默的失败管道比明显的失败更贵

`| Out-Null`、`$ErrorActionPreference` 没设、`try/catch` 吞掉异常 ——
这些在写脚本时是"让输出干净"的小事，在**做实验**时是销毁证据。

同一份代码在 CI 里跑和在本地跑，可能只是因为 CI **把错误打了出来**。

### 3. 记录"跑成了"比记录"跑挂了"更难

脚本在异常时中止，你会立刻发现。
脚本在**假装成功**时中止，你会几轮之后才发现。

所以脚本要么**大声失败**，要么**大声成功** ——
最坏的是"安静地跑了一个旧二进制，然后报告说一切正常"。

## 附带：同一次事故里的第二个坑

脚本是 `.ps1`，里面写了中文。**PowerShell 5.1 读无 BOM 的 .ps1 按 ANSI 解析**，
中文把字符串的引号配对搞乱了 → 整个脚本语法错误。

```
表达式或语句中包含意外的标记"for"。
```

这类"文件编码导致脚本被错误解析"的报错，报错位置和真正原因**完全无关**，
看起来像脚本写错了，实际是编码。

对策：`.ps1` 要么存成 **UTF-8 with BOM**，要么**整个脚本纯 ASCII**。
（本次选了后者 —— 脚本里的输出用英文，比加 BOM 更不容易再踩。）

## 检查清单

做自动化实验（变异测试、参数扫描、批量实验）时：

- [ ] 构建失败会**抛异常**，不会被 `| Out-Null` 吞掉？
- [ ] 每轮之前跑一次基线，数字必须和上一轮**完全一致**？
- [ ] "N 个变异全部存活"先怀疑装置，而不是先怀疑测试？
- [ ] `.ps1` 存成 UTF-8 with BOM，或者纯 ASCII？
- [ ] 脚本里写文件用的是 `[IO.File]::WriteAllText` 而不是 `Copy-Item`（mtime 问题见 `at-ninja-mtime-stale-binary.md`）？
