# 总数对得上，分部可以对不上

## 核心

2026-10-26，W7 结项之后还的第七笔（欠账 11）遇到的。

要给「文档里的数和现实对不对得上」加门禁。
最省事的是查**总数**：

```
文档写 2371，实测 2371 -> 绿
```

问题是：**总数相等，不代表每一份相等。**

```
套件 A  真实 100  文档 105
套件 B  真实 200  文档 195
                  -------
                  总数 300 = 300      <- 总数一模一样
```

**总数看着完全正常，而两个套件的数都是错的。**

## 这不是假想

本项目**已经栽过两次**，而且两次都是「总数正常」：

> 上一笔（`eb5b8cd`）记的断言数**低了 12**：
> `33dd280` 记 23 套件 / 2218 断言，真值 2230；
> `eb5b8cd` 记 24 套件 / 2251 断言，真值 2263。
>
> 而**根 README 和 W7 README 的套件表里也有 3 个套件的断言数是旧的**
> （`undo_redo` 151→152 / `run_engine` 99→111 / `headless_runner` 140→142）——
> 同一个根因，这次靠「重编全部目标」才发现。

而且还有一种**更阴**的形态：

> 有人把总数**改对了**（因为总数确实变了），
> 但套件表里**漏改了一行**。
>
> 这时候：
>   · 只查总数 → **绿**（总数确实对）
>   · 查逐套件 → **红**（那一行还是旧的）

## 修法

> **查逐套件，不只查总数。**
>
> 而且**套件名也要一起查** ——
> 只对数不认名字的话，
> 「两个套件的名字写反了」照样看不出来。

这一轮的检查器就是这么做的：

```
W7_VisionMasterLite/README.md 的套件表
  ↕  逐行比：名字 + 断言数
实测（CI 刚跑完那棵树）
```

26 行**逐个名字逐个数**都比，求和再比一次总数。

## 代价：得有一张**逐套件**的表

查不了分部，是因为**文档里没写分部**。
所以这张表得先存在 ——
它本来就该存在：**「每个套件有多少断言」只有一个存放处**，
那就是这张表。

⇒ 反过来推：**如果一个项目连逐套件的清单都没有，
那它的「总数」就永远只能靠手数**，
而手数的数**已经错了四轮**。

## 教训

> **总数是最容易对、也最会骗人的那个数。**
>
> 它对得上，只能证明**加法没错**，
> 证明不了**每一项没错**。
>
> ⇒ **能查分布的时候，不要只查总数。**
>
> 而「能查分布」的前提是：**那件事在文档里有一份完整的清单。**
>
> 没有清单就不要假装能查 ——
> 那时候查总数**不是**「查了个弱的版本」，
> 是**假装查过了**。
