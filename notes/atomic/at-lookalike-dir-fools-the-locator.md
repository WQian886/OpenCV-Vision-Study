# 靠名字猜出来的位置，会被同名的东西骗到

## 现象

测试要找到仓库根，办法是"从当前目录往上找，直到看见某个工程目录名"：

```cpp
static fs::path findRepoRoot() {
    fs::path p = fs::current_path();
    for (int i = 0; i < 8; ++i) {
        if (fs::exists(p / "W6_PCB_DefectProject") &&
            fs::exists(p / "W7_VisionMasterLite")) {
            return p;                 // 找到就停
        }
        if (!p.has_parent_path() || p.parent_path() == p) break;
        p = p.parent_path();
    }
    return fs::current_path();
}
```

看起来很稳：仓库根有这两个目录，往上走总会碰到。

**但 CI 的构建目录是 `build/ci/<工程名>/`** ——
于是 `build/ci/` 下面**正好有一份** `W6_PCB_DefectProject` 和
`W7_VisionMasterLite`（构建树的根，一个工程一个子目录）。

循环在 `build/ci/` 就停了，把**构建目录当成了仓库根**。

## 症状：报的是「文件不存在」，不是「根找错了」

```
[FAIL] 读得到 E:\...\build\ci\W5_OCR_QRCode\images\qrcode_test.png
```

看到这条，第一反应一定是"图没了"或者"路径写错了" ——
**没有人会想到"根找错了"**。查错方向完全不同。

而且它**不崩**、不空转，是老老实实报红 ——
所以它比"恒真空断言"好，但依然在**指错方向**。

## 为什么本地测不出来

本地构建目录是 `build/<工程名>/`，`<repo>/build/` 下面**没有**
`W6_PCB_DefectProject` 和 `W7_VisionMasterLite` 这两个名字
（工程目录叫 `W6_PCB_DefectProject`，但它在 `build/` **外面**）。

也就是说：**只有当构建目录的结构"长得像仓库"时，这个 bug 才会现形。**
而"构建目录按工程名分目录"恰恰是 CI 很自然的一种布局。

## 判据

**一个定位用的启发式，它的判据必须是"只有一处会有"的东西。**

- ❌ 工程目录名 —— 构建树里可以有一模一样的
- ❌ 目录结构像不像 —— 结构随时会变
- ✅ `common/`（共享代码目录）—— 只有仓库根有，
  构建树里不可能有同名子目录
- ✅ 更彻底：**别猜，让构建系统告诉你**
  （`target_compile_definitions(... W7_SOURCE_DIR="${CMAKE_CURRENT_SOURCE_DIR}")`）

## 两种修法

| 修法 | 做法 | 评价 |
|---|---|---|
| 换一个骗不到的标记 | 判据加上 `common/` 存在 | 改动小，保留"二进制在哪儿都能跑"的性质 |
| 让它告诉你 | 编译期把路径注进去 | 最彻底，但二进制绑定了机器 |

本项目两个都用了：
- 找**数据**（图、真值表、配方）用 `common/` 标记 —— 数据在源码树里，
  二进制换个地方跑也得找得到
- 找**源码**（`mainwindow.cpp`）用编译期注入 —— 源码的位置构建系统
  本来就知道，没有理由去猜

## 验证办法

**在一个"长得像仓库根"的目录里跑一次。**

比如把构建目录改成 `build/ci/<工程名>/`（CI 的常见布局），
或者更狠一点：在一个临时目录里造出那对同名子目录，然后从那儿跑测试。

如果你的定位逻辑只认名字，它当场就会错给你看。

## 检查清单

- [ ] 这个"往上找"的判据是什么？**只有一处会有**吗？
- [ ] 有没有可能存在一个**长得像**的目录？
- [ ] 找错了的时候，报错消息会指向**正确的原因**吗？
      （"文件不存在" ≠ "根找错了"）
- [ ] 这个 bug 在**只有 CI 才会出现的布局**下会现形吗？
- [ ] 构建系统明明知道的路径，为什么让测试去猜？
