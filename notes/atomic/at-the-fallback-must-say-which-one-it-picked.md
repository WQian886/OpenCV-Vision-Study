# 退而求其次的那个，也得说出来

## 一句话
> **「找不到就退而求其次」—— 如果输出里看不出来你挑了哪个，那就是静默失效。**

## 现象

`image_source_camera` 有一段挑相机的逻辑。原来的写法是：

```cpp
int selected = 0;                       // ← 默认第 0 台
for (unsigned i = 0; i < stDeviceList.nDeviceNum; ++i) {
    ...
    if (ip == cameraIp) { selected = (int)i; break; }   // 找到就改
}
// 没找到？selected 仍然是 0 —— 于是连第 0 台
```

用户填的是 `192.168.1.99`，实际接在网段上的是 `192.168.1.10`，
枚举到的第 0 台正好是 `192.168.1.10`。

于是：

- 连的是 `192.168.1.10`
- 输出里 `camera_ip` 写的是 **`192.168.1.99`**（用户填的那个）
- 不报错、不崩溃、日志干干净净

## 为什么它特别贵

**界面和实际跑的不是一回事。**

用户看到节点状态是绿的，输出里的 IP 和自己填的一模一样，
于是他会去查「是不是相机接错了」—— 而不是「程序没按我填的找」。

真正的问题（IP 填错 / 相机没接上 / 枚举到了别的网段的相机）
被这个兜底**掩盖**了。

## 判断标准：兜底能不能被看见

有些退而求其次是对的，有些是错的。分界线不是「有没有兜底」，
而是：

> **用户能不能从输出里看出来，你实际挑了哪个？**

| 兜底 | 说得清吗 | 判断 |
|---|---|---|
| 没找到就报错 | — | ✅ 最好：本来就只有一个正确答案 |
| 挑一个，但把实际挑的那个写进输出 | 说得清 | ✅ 可以接受 |
| 挑一个，但输出里报的是你以为的那个 | 说不清 | ❌ 静默失效 |

本例里**相机 IP 只有一个正确答案**，所以正确做法是**不兜底，直接报错**，
而且报错里要把**实际枚举到了哪些 IP** 都列出来：

```
没找到 IP=192.168.1.99 的 GigE 相机(枚举到 2 台: 192.168.1.10, 192.168.1.11)
```

这一条顺带钉住了另一件事：**IP 的字节序**。
SDK 给的是网络字节序（高位在前），换算写错的话，
列出来的 IP 会是乱的 —— 一条断言把两件事一起钉住。

## 教训

### 1. 「默认取第一个」是代码里最常见的静默失效

`int selected = 0;` 看着无害 —— 它只是个初值。
但它同时也是「**找不到时的行为**」。

> 写「初值」的时候问一句：**这个初值在异常路径上会被用到吗？**

### 2. 兜底和「明确只有一个正确答案」是两回事

- 曝光没给 → 用默认值（合理，默认值是**声明过的**）
- 相机 IP 对不上 → 连第一台（不合理，因为**只有一个正确答案**）

同样是"兜底"，一个该做，一个不该做。
区别在于：**这个旋钮是不是只有一个对的值**。

### 3. 报错要报「实际找到了什么」，不只报「没找到」

只说「没找到」的话，用户还是得自己去猜。
把实际枚举到的都列出来，用户一眼就知道该填哪个。

## 检查清单

- [ ] 代码里有没有 `selected = 0` / `index = 0` 这种**同时也是异常路径行为**的初值？
- [ ] 找不到的时候，是报错还是**悄悄挑一个**？
- [ ] 如果是悄悄挑一个 —— 输出里能看出来挑了哪个吗？
- [ ] 报错信息里有没有**实际找到的东西**（而不只是"没找到"）？
