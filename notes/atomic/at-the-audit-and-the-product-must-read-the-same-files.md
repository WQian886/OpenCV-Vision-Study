# 审计扫的源码，必须是产品真在编译的那份

## 核心
旋钮审计是**源码级**的：它读 `operators/*.cpp` 的文本，做静态检查
（死旋钮、没登记、抄副本）。

这套办法有个前提，从来没人写下来：

> **它读到的文件，必须是产品真在编译的那些文件。**

前提不成立的时候，审计**不会报错** ——
它会安静地查错东西。

## 三种坏法
| 坏法 | 审计会怎样 |
|---|---|
| 有人用脚本生成 `.cpp`，生成到别的目录 | 扫不到 → 算子数掉下去，用例 0 报红 |
| 有人把算子挪到别的目录 | 同上 |
| 有人加了新算子，**忘了加进 `CMakeLists.txt`** | **主程序根本没编它 —— 审计却在查它的旋钮** |

第三种最坏：审计对着一个**产品里根本不存在**的算子，
给出一份看起来很认真的结论
（"这个旋钮是死的"）—— 而产品里压根没有这个旋钮。

## 做法
用例 7 做**双向**核对：

- 磁盘上 `operators/*.cpp` 每个都必须在主程序的 `set(SOURCES ...)` 里
  （不在 → 主程序没编它，审计在查一个不存在的东西）
- `set(SOURCES ...)` 里列的每个都必须在磁盘上真的存在
  （不在 → CMake 早晚会报错，审计先说清楚）

⚠ 查 `CMakeLists.txt` 要按 **CMake 的注释规则**切（`#` 到行尾），
不能拿 C++ 那套（`//`、`/* */`）去切 ——
注释里写着 `operators/xxx.cpp` 的时候，那是**说明**，不是真的在编译。

## 教训
> **一个查不到问题的审计，比没有审计更坏。**
> 因为它让人以为有人看着。

所以每个 lint 都要能回答两个问题：

1. 我查的东西**非空**吗？（用例 0）
2. 我查的东西**是产品真在用的**吗？（用例 7）

第一条防的是「空断言长得很像通过」，
第二条防的是「查错了对象也长得很像有结论」。

推论：写 lint 的时候，别只问"我想查什么"，
还要问"**我读的是不是那份东西**"。
