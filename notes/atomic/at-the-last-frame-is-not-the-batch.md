# 末帧判定不等于整批判定：拿末帧当整批，就是漏检

## 核心

2026-10-24，W7 结项之后还欠账时遇到的。

一条流水线跑 30 帧（抽检），第 7 帧判废，第 8~30 帧都正常。
程序最后说什么？

```
GUI      : 「⚠️ 有 1 帧判废,整批判 NG」      ← 对的
headless : final_result = "PASS",退出码 0   ← 漏检
```

CI 看到退出码 0，就说「过了」。

## 为什么两个会不一样

因为**「末帧判了什么」和「这一批是什么结论」是两件事**，
而 headless 的退出码是拿前者推出来的：

```cpp
// 改之前的 headless_cli.cpp
if (res.errorCount > 0) { ...; return 3; }
if (res.finalResult == QStringLiteral("FAIL")) return 1;   // ← 这里
return 0;
```

`res.finalResult` 是**末帧**的判定。于是第 7 帧判废这件事，
在这一行里**根本不存在** —— 它只看得见最后一帧。

而 GUI 那边的判据是对的（任一帧判废就是 NG），它的注释也早就写对了：

> 只看最后一帧的 PASS/FAIL 是不够的：
> 抽检 30 帧里 1 帧有问题，末帧正常的话单看末帧就是漏检。
> **产线的判废看的是整体，不是抽一张。**

> 讽刺的是，这句注释和那段代码**在同一个仓库里**。
> 一份写着正确答案，一份写着错误答案，**而且两边都是绿的**。

## 漏检为什么特别贵

抽检漏检和完全漏检不一样：

- 完全漏检（一帧都不跑）会**报错**，人会去看；
- 抽检漏检（30 帧里漏了 1 帧）**一切正常** ——
  退出码 0、状态点全绿、日志干干净净。

> **「判废算子在漏检时判合格」和「整批判定只看末帧」是同一族病：**
> 一个是判据错，一个是取样错。
> 共同点是：**结论看起来完全正常。**

## 收法：把两种判定分开命名

现在这两个概念各有各的名字，互不冒充：

| 概念 | 是什么 | 谁在用 |
|---|---|---|
| **末帧判定** | 最后一帧判了什么 | 结果 JSON 的 `final_result` |
| **整批判定** | 这一批是什么结论（任一帧判废 / 任一帧跑坏 / 中止） | 结果 JSON 的 `batch_verdict`、CLI 的退出码 |

规则收成**一份**（`W7_VisionMasterLite/frame_verdict.h`），
两个调用方都用它，**谁也不许自己再推一遍**。

### 判据

```
整批判定 = Cancelled > Errored > Failed > Passed
```

- **Cancelled**（被手动 Stop）最高：跑完的那几帧全 PASS 也不代表整批合格；
- **Errored**（有帧跑坏了）次之：跑坏的帧**连判都没判成**，
  比判废更「不成结论」；
- **Failed**（有帧判废）；
- **Passed** 兜底。

### 什么时候用哪个

- **CI / 退出码** → 整批判定。CI 要判的是「这一批过没过」。
- **给用户看** → 两个都要给。多帧时末帧判定和整批判定**可能不一样**，
  只摆一个会误导 —— 用户看见「末帧 PASS」就以为整批过了。

## 还有一个孪生的坑：空头的 PASS

同一个地方还藏着**另一种**混用：

> 判定节点说 PASS，不代表整条流水线跑成了 ——
> 上游报过错，那个 PASS 就是**空头**的。

所以「有步骤报错」时，最终结果必须强制说 **ERROR**，不许说 PASS。

这两种混用（末帧 vs 整批、空头 vs 真实）有个共同点：

> **它们产出的都是一个「看起来正常的错结论」。**
> 所以必须**在代码里分成两个名字**，
> 而不是靠注释提醒 —— 注释会骗人，断言不会。

## 教训

> **「末帧判了什么」和「这一批是什么结论」是两件事。**
> 拿前者当后者，就是**漏检** ——
> 而且是那种**一切看起来都正常**的漏检。
>
> 收法不是「记得看全部帧」，是**把两种判定分成两个名字**，
> 各有各的出口，然后**只准有一处算**。
>
> 顺带记一条：判定节点说 PASS ≠ 流水线跑成了。
> 上游报过错，那个 PASS 是**空头**的 ——
> 所以有错时必须强制 ERROR。
>
> 两种混用都靠注释挡不住，因为**注释和错误代码在同一个仓库里，两边都是绿的**。
