# 教科书的公式不等于库的实现

## 核心

2026-10-26，给 W2 补测试时量到的。

焊点颜色 BGR(60,180,220)（金黄）。
教科书上的 8bit HSV 色相公式：

```
H = 60 * (g - b) / delta        // delta = max - min
```

代进去算出来是个 45 附近的数（换个写法是 15 / 165 一类的补角）。

**OpenCV 实测：H = 23。**

## 为什么差这么多

OpenCV 的 8bit HSV **色相只有 0..179 一圈**（不是 0..359）。
它的公式是：

```
H = (g - b) * 30 / delta
```

**比教科书少一半。**

> 换句话说，**教科书那个公式算出来的色相，
> 放在一个只有 180 度的空间里，位置是错的**。
>
> 不是算错了小数点，是**坐标系不一样**。

## 要命的地方

如果我**按教科书的数去「修」那个 HSV 窗口**，
我会把一个**本来正确的窗口改错** ——
改出来的窗口**选不中焊点**。

而且画面上**看着还能用**：
背景还是绿的，焊盘还是金的，只是**蒙版糊了**。
肉眼看输出图，很难判断「比改之前差」。

**这是一个「不存在的 bug」，而我的算术制造了它。**

## 差点发生的版本

我在写断言之前先在心里算了一遍：
「焊点的色相应该是 45 左右，那我把窗口改成 H=40..60 好了。」

**写探针量了一下 —— H=23，窗口 H=10..30 本来就是对的。**

**于是没改。**

> 「没改」也是一种结论，
> 而且是**最难自己得出的那一种** ——
> 因为你不会有任何东西提醒你「你本来要修的那个 bug 不存在」。

## 教训

> **要写进代码的数值，必须在这个库上量出来。**
>
> 不是从书上抄的，不是从别的库抄的，
> 不是从记忆里抄的。

理由有两条：

1. **抄来的数有出处，所以特别难被发现是错的。**
   一个 `0.25` 看着眼熟，一个 `60*(g-b)/delta` 看着更眼熟 ——
   **越眼熟越不容易被质疑。**
2. **「不存在的 bug」是最贵的 bug** ——
   为了修它而做的改动，会引入**真的** bug。

## 怎么量

一行探针就够，**不量就是猜**：

```cpp
cv::Mat hsv;
cv::cvtColor(bgr, hsv, cv::COLOR_BGR2HSV);
const int h = hsv.at<cv::Vec3b>(0, 0)[0];   // 8bit 色相，直接读出来
```

**色相、饱和度、明度三个通道都可以直接读** ——
不需要推公式，不需要对照论文。
