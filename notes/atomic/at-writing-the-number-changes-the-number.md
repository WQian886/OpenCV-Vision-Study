# 写下这个数的那一刻，这个数就变了

## 核心

> **文档里写的那个数，会被「写文档」这个动作本身改掉。**
>
> 所以：**量必须放在最后一步**，而且**每写一段就要重量一次**。

## 现象（2026-10-26，CI 在真 runner 上跑绿那一轮）

这一轮要给文档补「CI 第一次在真 runner 上跑绿了」这一章。
那一章落在 `notes/notes_CI_2026-10.md` 里 ——
**而那篇笔记的体积，正是文档里写着的一个数**（`~997 KB`）。

于是：

| 我改了什么 | 量出来 |
|---|---|
| （改动之前）| 997 KB |
| 加了第十章 + 核实清单表 + 改写 §3.3 / §4.7 | **1002 KB** |
| 给「第一次真跑」那篇补上结局 | **1003 KB** |
| 把台账里那一句「跑起来了」改成「跑绿了」 | **1004 KB** |

三次，每次都是同一件事：
**我改了一样和那个数「无关」的东西，那个数就过期了。**

## 为什么它反直觉

那个数（notes 体积）看起来是**背景数据** ——
「这些笔记一共占多大地方」——
和「我在写哪一段」毫无关系。

但它**不是背景**：
它量的是**所有笔记的总和**，
而我写的每一段**都进这个和**。

⇒ 这跟「文件清单里列着清单自己」是同一类：
**被量的东西，包含「量它」这个动作本身。**

## 判据

> **问一句：这个数会不会因为「我正在改东西」而变？**
>
> 会 ⇒ 它**不能**在改动**之前**定下来。

## 修法

1. **量在最后**：内容全改完，最后一次测量，最后一次写入。
2. **每写一段重量一次**：这一轮改了三次，就量了三次。
3. **交给机器**：仓库里 `tools/check-doc-numbers.ps1`（CI 的 Step 3c）
   **每次都在工作树上重新量**，20 条断言对不上就红 ——
   它抓的是「文档里的数 ≠ **现在的**树」，不是「≠ 某次快照」。
4. ⚠ **写回去的新数字，本身也是被量的一部分**：
   改数字会改字节数，字节数会改那个数。
   这一轮 `997 → 1002 → 1003 → 1004` 恰好**都是 4 位**，
   所以改数字本身没有再推高体积；
   **位数一变（`999 → 1000`）就得多量一次**。机制在这儿。

## 推论

> **凡是被引用进文档的测量值，都是「会过期」的** ——
> 区别只在于：**它是被机器守着过期，还是被你记着过期。**
>
> 这一轮 20 条文档断言全绿，
> 不是因为我算得准，
> 是因为**每写一段就重量一次**，
> 而且**最后还有一道机器门禁**兜着。

## 检查清单

- [ ] 我写的这个数，会因为**我正在写的东西**而变吗？
- [ ] 这个数是**最后**一次量的吗？
- [ ] 写回新数字之后，体积/行数会不会**又变一次**（跨位数时）？
- [ ] 有没有一道**机器门禁**在盯着它？
