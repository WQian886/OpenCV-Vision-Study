## 一、为什么要抽共享核心

### 1.1 【实测·项目】两边各写一份，实测差距有多大

W7 早就把判定改成了**配方驱动 + 逐条标定**的版本；W6 那边还是写死的：

```cpp
// W6 改造前：六处 `if (label == "R2")` 规则分派
```

拿另外三种板型直接跑 W6，实测结果：

| 板 | 期望 | W6 改造前实测 |
|---|---|---|
| 三块**好板** | PASS | **全被判废**（误报 3/3）|
| 两块**废板** | FAIL | 输出与好板**逐字相同**（等于没检）|
| 元件数 | 随图变化 | **恒等于 6**，与图上实际有什么无关 |

根因不是"坐标写死了"，而是**规则也写死了** —— 换一块布局不同的板，
坐标不对，规则更是一条都跑不了。

### 1.2 【实测·项目】"抄一份到 W6"就是本项目栽过四遍的坑

W6 要的是 W7 的算法。把 W7 那份抄过来，是这个仓库**已经栽过四遍**的做法：

| # | 抄的是什么 | 漂开后的后果 |
|---|---|---|
| 1 | `EXPECTS[6]` 真值表 | 期望值与实际脱节 |
| 2 | `lo[0]` 越界守卫 | 越界不报错 |
| 3 | 守卫本身 | 守卫守了个空 |
| 4 | **两处金层掩膜** | 定位和判定各用各的掩膜，**56/56 测试全绿** |

第 4 次最贵，因为**连测试都是绿的**。抄出来的那份会随 W7 的标定一起漂，
漂了没人知道 —— 而这次抄的东西恰好就是"判定"本身，漂了就是废板判合格。

所以：**把判定抽成两边都调的那一份**，而不是"抄一份过去"。

### 1.3 【实测·项目】为什么放仓库根的 `common/`，不放 W7 里

W6 不引 Qt。核心如果依赖 Qt，就是给一个命令行项目加依赖；
反过来放进 W7，W6 就要反向依赖 W7 —— 一个命令行工具依赖一个 Qt 应用，更别扭。

```
common/pcb_core/          ← 无 Qt 依赖,只依赖 OpenCV + 标准库
  ├── pcb_core.h/.cpp     配方解析 + 定位 + 六条判据 + 短路
  ├── pcb_color_ref.h     颜色判据(去绝对化后从 W7/operators 搬来)
  └── mini_json.h/.cpp    无依赖 JSON 读取器
```

两边各自在自己的 `CMakeLists.txt` 里把**同一份源文件**链成静态库：

```cmake
add_library(w6_pcb_core STATIC ${PCB_CORE_DIR}/pcb_core.cpp ${PCB_CORE_DIR}/mini_json.cpp)
add_library(w7_pcb_core STATIC ${PCB_CORE_DIR}/pcb_core.cpp ${PCB_CORE_DIR}/mini_json.cpp)
```

配方 JSON **只有一份**，留在 `W7_VisionMasterLite/recipes/`，W6 不复制 ——
复制就是抄副本。W6 用相对路径读它，构建时拷一份到 exe 旁边。

## 二、抽出来的新代码一行测试都没有（这才是重点）

抽完之后，`common/pcb_core/` 里有两块**全新写、零覆盖**的代码：

### 2.1 【实测】mini_json：200 行手写 JSON 解析器

解析器是典型的"平时对、边界炸"的东西。炸的方式分三类：

| 类 | 表现 | 危险度 |
|---|---|---|
| (a) 位置算错 | 报错指向错误的字符位置 | 难查，但不致命 |
| (b) **静默解析错** | 把坏 JSON 解析成"看起来对"的值 | **致命** |
| (c) 边界 | 空容器、转义、UTF-8、深嵌套 | 看运气 |

(b) 为什么致命：解析器返回 false 时上层会报"配方非法"，这是好事；
返回 true 但**值错了**，上层拿着错配方往下跑 —— 报出来的结论是编的。
所以每条 happy path 都要**核对值**，不能只 `check(!failed)`。

**实测抓到的两个真 bug**（写测试之前没人发现过）：

```
mini_json 接受前导零 "01"    → 严格 JSON 不允许，QJsonDocument 也不允许 → 已修
截断 JSON 的报错说"内容为空" → 误导（真因是少引号/少括号）              → 已修
```

### 2.2 【实测】parseRecipeJson 的 6 类错误分支

W7 原来那份 `board_recipe.cpp` 里也有同样的校验，但**同样没被测过**
（grep 过：现有套件只走 happy path）。而这些校验守的正是"废板判合格"那条路：

```
规则名拼错  → 那条规则一条都不跑，而且不报错 → defects 为空 → PASS
sites 为空  → "0 个元件，零缺陷，PASS" —— 什么都没查却报合格
位号重复    → 报告里出现两个 R1，排查时成了猜谜
```

核心的策略是**少一个必填字段就报错，不做部分加载**。
部分加载最阴险 —— 加载出 5 个站点、另外 3 个静默丢了，
判定环节照样输出结论，只是少查了三块板。

### 2.3 【实测】核心的两条"拒绝给结论"的路

| 触发条件 | 后果（如果拒绝失效）|
|---|---|
| 一个元件都没配规则 | 规则一条都跑不了 → defects 为空 → PASS |
| 曝光撞 8 位色深上限 | 错色判据恒假 → defects 为空 → PASS |

两者都是"废板判合格"，而且**都不报错**。所以必须专门测。

## 四、W6 拆成可测层：main.cpp 里的逻辑没法被测

### 4.1 【实测·项目】入口文件是链接不上的

W6 的逻辑原本全在 `main.cpp` 里。`main.cpp` 是**程序入口**，
别的目标链接不了它 —— 于是 **W6 一条自动化测试都没有**。

而 W6 恰恰是最需要测试的一层：它决定**哪些图被检了**。

仓库里已有同样的先例：W7 的 `step_scope.h` 就是这么从 `mainwindow.cpp` 里抽出来的
（见那个头文件的说明）。W6 这层是同一个道理：

```
w6_cli.h/.cpp   纯逻辑:查板型、找配方、跑一块板、跑一批板、拼 CSV 行。给输入出结果,不打印
main.cpp        入口:解析参数、把结果打印成人话
```

### 4.2 【实测】搬的过程中自己抄了一份，又抓回来

抽 `runReport` 的时候，"把缺陷按元件归拢"这段逻辑在 `runBaseline` 和 `runReport`
里各写了一份 —— 正是本项目要避免的抄副本。改成共用函数 `rowsFromBoard()`。

### 4.3 【实测】这次测试抓到的三个真 bug

| # | 症状 | 根因 |
|---|---|---|
| 1 | `board_file` 列写的是 `report/baseline.csv,R1,...` | 一个 `path` 参数**既当报告输出路径又当板文件名** |
| 2 | `images/complex/` 里 9 块板被静默跳过 | 用**非递归** `directory_iterator` |
| 3 | 非 ASCII 路径直接崩 | 见下一节 |

第 2 条是最典型的"静默失效"：报告看着完整（17 张图里少 9 张），
但看报告的人看不出来少了什么。改递归之后，**跳过项必须逐条列出原因**。

## 五、这次逮到的真 bug：路径编码（详见 atomic 卡）

### 5.1 【实测】现象

测试跑到"查不到板型"那一步，进程直接崩了（`0xC0000409`），
而且**不是断言失败**，是整个测试进程死掉。

### 5.2 【实测】根因：MSVC 的窄串按 ANSI 代码页解释

本机 ACP = 936（GBK）。用探针实测：

```
[1] path / "中文"        构造 THROWS: No mapping for the Unicode character exists in the target multi-byte code page.
[2] path(L"中文")        构造成功, .string() 长度 25
[3] path / "plain.png"   构造成功, .string() 长度 16
```

两处坑：

1. **窄串构造路径**（`p / "中文"`）：窄串按 **ANSI** 解释，而源文件是 UTF-8 → 直接抛异常。
2. **`path::string()`**：把宽路径转回**ANSI** → 非 ANSI 字符直接抛异常。

### 5.3 【实测】更危险的那一半：不崩，是静默跳过

即使绕开崩溃（用宽路径构造），`imgPath.filename().string()` 拿到的是 **GBK 字节**，
而 `manifest.csv` 是按**原始字节**读的 **UTF-8** —— 两边编码不同，
**中文名永远比不出来** → "查不到板型" → 这块板被**静默跳过**。

在报告里，被跳过的板和合格的板长得一模一样。

**修法**：路径统一走 UTF-8（`generic_u8string()`），文件名和 CSV 内容同一套编码；
读图改用 `imdecode`（`cv::imread` 内部按 ANSI 打开文件，中文路径读不出来，
而且**不报错**，只给你一个空 Mat）。

## 六、变异验证

### 6.1 W6 CLI 层：4 个变异，4 个全杀（基线 142 断言）

| # | 改法 | 红 |
|---|---|---|
| M1 | `boardKindOf` 退回 `.string()`（还原编码 bug） | **3** |
| M2 | `runReport` 退回非递归遍历（还原漏检 9 块板） | **5** |
| M3 | 多个缺陷只写第一个 | **3** |
| M4 | `csvEscape` 不转义 | **5** |

M1 的失败信息直接复现了故障形态：

```
[FAIL] 中文文件名也查得到板型(实际 "")
[FAIL] 中文名板子被判了 1 块(实际 0)
[FAIL] 中文名板子没有被跳过(实际跳过 1)
```

M2 的失败信息是本项目最想要的那种：

```
[FAIL] 判过的(8) + 跳过的(4) = PNG 总数(21)
[FAIL] complex/ 里 9 块板都被判了(实际 0)
[FAIL] 每张 PNG 都有交代(9 张下落不明,例如 complex/mcu_baseline.png)
```

最后一条是**总纲式断言**：判过的 + 跳过的 = PNG 总数。
一张图都不许悄悄消失 —— 少一张，报告上就少一块板，而看报告的人看不出来。

### 6.2 W7 帧接线：变异让套件转红（上一轮已做）

把 `shouldCacheFrame` 改回 `frame == totalFrames - 1` → `run_policy` 立刻转红（`pass=161 fail=1`），
而这个变异以前是 12/12 全绿。

### 6.3 【实测】一次假阴性的自坑，值得单独记

第一次跑变异脚本，4 个变异**全部报"没抓到，套件仍然全绿"**。

第一反应是"我的测试没有牙"。真相是：**构建根本没成功** ——
脚本里没初始化 MSVC 环境（`INCLUDE`/`LIB` 缺失，`cl.exe` 连 `<limits>` 都找不到），
ninja 编译失败，**旧 exe 还在原地**，跑出来的当然是绿的。

如果当时照着表面结论走，就会去给一套其实有牙的测试补断言 ——
或者更糟，写下"变异存活"这种结论。

**对策**：脚本里构建失败必须**抛异常**，不能被 `| Out-Null` 吞掉。
详见 atomic 卡 `at-build-failure-looks-like-mutation-survived.md`。
