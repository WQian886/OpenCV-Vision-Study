## 2. 为什么它们之前是 0 个测试

不是因为不重要。

W1 整个项目**只有一段活着的代码** —— 「练习 3：把蓝色像素涂黑」，
而那段代码**一行测试都没有**。

原因是**它写在了 `main()` 里**：

```cpp
int main() {
    ...
    for (int y = 0; y < img.rows; ++y)
        for (int x = 0; x < img.cols; ++x) {
            cv::Vec3b& px = img.at<cv::Vec3b>(y, x);
            if (px[0] > 100 && px[1] < 150 && px[2] < 150) {   // <- 判据在这
                px = cv::Vec3b(0, 0, 0);
            }
        }
    cv::imshow(...);      // <- 窗口在这
    cv::waitKey(0);       // <- 阻塞在这
}
```

一个要**开窗口、等人按键盘**的函数，**没法做无头测试**。

所以补法的第一步不是「给 `main.cpp` 加个开关」，而是
**把纯逻辑拆出来**：

| 项目 | 拆出来的文件 | 里面是什么 |
|---|---|---|
| W1 | `W1_ImageIO/pixel_ops.{h,cpp}` | 造图 / 判据 / 涂黑，三个函数 |
| W2 | `W2_ColorFilter/color_pipeline.{h,cpp}` | 整条处理链 + **全部常量** |

`main.cpp` 和测试套件**链的是同一个 `.cpp`**（同一个源码进两个 CMake 目标）。

### 为什么不让测试「自己抄一份」

抄出来的副本会随核心漂移：

> 改了判据，测试还在按旧判据断言，
> 于是测试「绿着」而 demo 已经变了。
>
> **绿灯什么也没证明。**

这是本项目栽过四遍的「抄副本」。仓库里已有的同样做法：
W6 的 `w6_cli.cpp`、W7 的 `w6_cli.cpp` / 纯层头文件。

W2 还顺带解决了一件事：**常量以前散在 `main.cpp` 里**。
现在焊盘矩形、焊盘颜色、金色 HSV 窗口**只在 `color_pipeline.cpp` 里定义一次**。

## 3. 断言从哪来：每个门槛都是**量出来的**

写断言最容易犯的错是**拍一个数**。
本轮所有非平凡的门槛都是**先量、再写**，而且**留了余量**。

### W2 的量测结果

| 量 | 实测 | 断言门槛 |
|---|---|---|
| 焊点 BGR(60,180,220) 的色相 | **H=23** | 窗口 H=10..30 |
| 窗口罩住焊点 | **87.0%**（最差一块 86.5%） | ≥ 75% |
| 背景误选 | **0.60%** | ≤ 2% |
| 平坦区标准差 | 23.78 → 高斯 6.56 / 中值 6.22 / 双边 6.25 | < 原始的 1/3 |
| 阶跃边缘过渡带 | 原始 0 列 → 高斯 **4** 列 / 双边 **0** 列 | 高斯 ≥ 2，双边 ≤ 1 |
| 椒盐噪声后取值范围 | 中值 **[40,40]** / 高斯 [31,94] | 中值必须 == 40 |
| 光照不均暗区的前景像素 | 固定阈值@127 **0** 个 / 自适应 **20000** 个 | 固定 0，自适应 ≥ 1000 |

门槛都留了余量，因为**噪声的实现细节可能随 OpenCV 版本变**。
卡死在一个实测值上的门槛，就成了「只有这台机器成立」的断言 ——
那正是本仓库在 CI 第一次真跑时栽过的坑。

## 4. 教科书给的是 H=45，OpenCV 给的是 H=23

这一轮**最值钱的一条**。

焊点 BGR(60,180,220)，教科书上的 8bit HSV 色相公式是：

```
H = 60 * (g - b) / delta        // delta = max - min
```

代进去：`(180-220) = -40`，`delta = 220-60 = 160` → `H = 60 * (-40) / 160 = -15` → 折到 165。

（换成黄色算式 `60*(b-g)/delta` 也是 15/165 一类的数，总之**在 45 附近或它的补角上**。）

**但 OpenCV 实测是 H=23。**

原因：OpenCV 的 8bit HSV **色相只有 0..179 一圈**，
它的公式是 `(g-b)*30/delta` —— **比教科书少一半**。

> 也就是说，**教科书那个公式算出来的色相，在一个只有 180 度的空间里，
> 位置是错的**。

**如果我按教科书的数去「修」这个 HSV 窗口，
我会把一个本来正确的窗口改错** ——
改出来的窗口**选不中焊点**，而且画面上看着「好像还能用」。

⇒ 这就是**先量再改**的价值：
**量出来发现没有 bug，就没有改**。
「没改」也是一种结论，而且是最难自己得出的那种。

**教训**：

> **教科书的公式不等于库的实现。**
>
> 凡是要写进代码的**数值**（阈值、窗口、色相、系数），
> 都应该是**在这个库上量出来的**，
> 而不是从书上抄来的。
>
> 抄来的数**看起来**有出处，所以**特别难被发现是错的**。

详见 [atomic/at-the-book-formula-is-not-the-library.md](./atomic/at-the-book-formula-is-not-the-library.md)。

## 5. 变异验证：把实现改坏，测试**必须**转红

新写的测试**自己也是可能错的**。
一个从来没红过的测试，和一个摆设差不多。

所以这一轮**主动把实现改坏**，看测试会不会叫：

| # | 改了什么 | 结果 |
|---|---|---|
| 1 | W1 判据 `px[0]` → `px[2]`（把 BGR 当成 RGB） | **8 条断言转红** ✓ |
| 2 | W2 金色窗口上限 30 → 60 | **2 条断言转红** ✓ |
| 3 | W2 `bilateralDenoise` 内部换成高斯 | **0 条转红** ✗ —— 见下一节 |

第 1 条正是 W1 测试文件头里点名要防的那个 bug
（「判据写成 RGB，白底会整片被判成蓝，而画面上看不出任何异常」）。

### 第 3 条抓到的是**我自己的测试**

变异 3 用了**0 条断言**来抓它 —— 这不对。

查下去发现：那条断言量的是
**`cv::bilateralFilter` 的输出**，而不是 **`w2::bilateralDenoise` 的输出**。

测试里写的是：

```cpp
cv::Mat sg, sb;
cv::GaussianBlur(step, sg, cv::Size(9, 9), 0);     // <- 直接调 OpenCV
cv::bilateralFilter(step, sb, 9, 75, 75);           // <- 直接调 OpenCV
```

**它量的是「OpenCV 的双边滤波好不好」，
测的却是「我们的实现对不对」** ——
这两件事长得一模一样，但**根本不是一件事**。

把 `w2::bilateralDenoise` 的实现整个换成高斯，
这条断言**照样绿**。

**改法**：测试调 `w2::` 的函数，不调 `cv::` 的：

```cpp
const cv::Mat sg = w2::gaussianBlur(step, 9);
const cv::Mat sb = w2::bilateralDenoise(step, 9, 75, 75);
```

改完之后再跑同一个变异 → **1 条断言转红** ✓。

⇒ **变异验证不只是「证明测试有效」，
它还是「找出测试哪里测错了对象」的唯一手段。**
因为「测试没反应」这个现象本身，只有靠**故意改坏**才看得见。

详见 [atomic/at-the-assertion-measures-the-library-not-you.md](./atomic/at-the-assertion-measures-the-library-not-you.md)。

## 6. 顺手改掉的两个东西

### 6.1 没人检查的表会漂

`tools/check-doc-numbers.ps1` 原来**只查 W7 的套件表**。
这一轮把它改成**每个项目都查自己的表**。

一改就逮到 **W6 的表漂了**：

| | `pcb_core` | `qr_ocr` | `w6_cli` | 合计 |
|---|---|---|---|---|
| W6 README 的表（错的） | 180 | 36 | 163 | **379** |
| 实测（对的） | **279** | **36** | **167** | **482** |

**而同一份 README 上面那段正文写着「3 个 ctest 套件、482 条断言」** ——
**两份数字就摆在同一个文件里，谁也没对一眼。**

这个漂能存在这么久，就是因为**检查器没看这张表**。
一个没人检查的表，就是一个会漂的表。

⇒ 详见 [atomic/at-the-table-nobody-checks-drifts.md](./atomic/at-the-table-nobody-checks-drifts.md)。

### 6.2 PowerShell 变量名**不区分大小写**

改检查器的时候踩了一个坑，值得单独记一笔：

```powershell
$Measured = @{ 'W7_VisionMasterLite' = @{...}; 'W6_PCB_DefectProject' = @{...} }
...
foreach ($pt in $SuiteProjects) {
    $measured = $Measured[$proj]      # <- 和 $Measured 是**同一个变量**！
```

**PowerShell 的变量名不区分大小写**，
`$measured` 和 `$Measured` 是**同一个变量**。

于是第一次循环把**外层表**覆盖成了 **W7 的内层表**，
第二次循环拿 `'W6_PCB_DefectProject'` 去 W7 的套件表里找 → `$null` → 崩。

报错是 `The property 'Count' cannot be found on this object` ——
**它不告诉你「你的变量名撞了」**，只告诉你「这个对象没有 Count」。

⇒ 详见 [atomic/at-powershell-names-ignore-case.md](./atomic/at-powershell-names-ignore-case.md)。

### 6.3 链接不知道它的目标已经没了

这一轮**删掉了一张 atomic 卡**（重复的那张，内容折叠进旧卡当「复发 N 次」）。

**删掉是对的。** 但**三张别的卡还指着它**。

而**没有任何东西报过错** ——
链接的文字还是那么好看，markdown 还是照常渲染，**CI 是绿的**。

关键在于：**链接本身一个字都没变**。
变的是**它指的那个文件没了**。

⇒ **盯着链接看是看不出来的，只能跟着走一遍。**

于是加了 `tools/check-links.ps1`（CI 的 Step 3d），
第一次跑就逮到**另一个**坏链接 —— 而且它跟这一轮毫无关系，
是**早就坏在那儿**的：

```
W7_VisionMasterLite/README.md:
  [operator_library_groups.h](W7_VisionMasterLite/operator_library_groups.h)
```

这个 README **就在 `W7_VisionMasterLite/` 里面**，
所以那个路径指的是 `W7_VisionMasterLite/W7_VisionMasterLite/...` ——
**多了一层**，不存在。它想指的是上一层那个。

写完检查器，照例做**变异验证**：

| # | 改了什么 | 期望 | 实测 |
|---|---|---|---|
| 1 | 指向一个不存在的卡 | 红 | **红 ✓** |
| 2 | 路径多一层目录（就是上面那个真 bug） | 红 | **红 ✓** |
| 3 | C++ 代码里的 `](`（`auto hook = [&](...)`） | **绿** | **绿 ✓** |

第 3 条是**反向**验证 ——
检查器如果把代码块里的 `](` 当链接，它会**误报**。
而一个天天误报的检查器，大家会学会忽略它，
**然后它就等于不存在**。

而检查器**自己**也被这个坑绊了一次 ——
第一版跑出来是**红的**，那个红来自**它自己**：
它没跳过**行内代码**，而且把 `qsizetype i` 切成了 `qsizetype`
（markdown 的**裸目标不能带空格**）。

> **「检查器报错了」的第一反应应该是「检查器错了」**，
> 不是「文档错了」——
> 否则就会把一段**正确的 C++ 代码**改成能骗过检查器的样子。

⇒ 详见 [atomic/at-a-link-does-not-know-its-target-is-gone.md](./atomic/at-a-link-does-not-know-its-target-is-gone.md)。

### 6.4 顺带发现：README 的**每份笔记大小表**也漂了

查链接的时候顺手量了 README 里那张「每份笔记多大」的表 ——
**30 行里错了 8 行**，其中一个差了 **29 KB**
（`notes_CI_2026-10.md` 写着 19 KB，实际 48 KB）。

而**总数一直是对的** ——
因为一行的错可以被另一行的错抵消，
**和「总数对得上但分布对不上」是同一个病**
（见 [atomic/at-the-total-can-hide-a-wrong-part.md](./atomic/at-the-total-can-hide-a-wrong-part.md)）。

⇒ 把它也接进门禁：`tools/check-doc-numbers.ps1` 现在**逐份**对大小，
而且要求那张表和 `notes/` 目录**一一对应**
（**存在却没列出来的笔记**，也是漂）。

## 7. 还有一个坑：**恢复文件没改时间戳 → 跑的是旧二进制**

变异验证完要把实现**改回去**。我用的是
`Copy-Item <备份> <原文件>`。

结果：MSBuild 认为**没变过**，**不重编**，
于是 ctest 跑的**还是那个变异过的二进制** ——
**8 条断言红着，而我以为已经恢复了。**

差点就把它当成「恢复失败」或者「测试不稳定」记进笔记。

改法：恢复之后**显式更新修改时间**：

```powershell
(Get-Item $file).LastWriteTime = Get-Date
```

⇒ 详见 [atomic/at-ninja-mtime-stale-binary.md](./atomic/at-ninja-mtime-stale-binary.md)
（那张卡已经记了**五次**复发，这次是第五次）。

这个坑本仓库**栽过很多次**：
memory 里那条「旧二进制伪装成假红」，
以及 [atomic/at-ninja-mtime-stale-binary.md](./atomic/at-ninja-mtime-stale-binary.md)
（那张卡记了**五次**复发，这次是**第五次**）。

**同一个坑第二次遇到**说明「知道这个坑」和「不会再踩这个坑」是两件事 ——
所以这次**记进那张已有的卡**，而不是另开一张。

> ⚠ 一开始我**另写了一张新卡**
> （「恢复文件没改时间戳」）。
> 入库前拉全量标题查重时才发现：
> 那张新卡的**根因、现象、修法**
> 已经被现有那张卡**一字不差地记过了**。
> ⇒ **写卡之前先查重**，
> 重复的卡**收进旧卡当一节「复发 N 次」**，而不是新增一张。
>
> 这个仓库的规矩是**一卡一概念**——
> 两张卡讲同一个概念，等于**同一个概念有了两个版本**，
> 而其中一个版本一定会开始漂。
